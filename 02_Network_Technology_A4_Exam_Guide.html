② RTT / RTO (Q1) ★★★
Est = (1−α)Est + α·Sample α=0.125
Dev = (1−β)Dev + β|Sample−Est| β=0.25
RTO = Est + 4·Dev
RTO ต่ำไป (เช่น 3ms ในกราฟ 3–7ms) → Premature timeout → ส่งซ้ำโดยไม่จำเป็น → เปลือง BW + cwnd ลดผิด ๆ
RTO สูงไป → ถ้าหายจริง รอนาน → Slow loss recovery throughput ตก
RTO=8ms (กราฟ 3–7) → ครอบคลุม ✓ ไม่ timeout เกิน
ตั้งให้ดี: ต้องดู ค่าเฉลี่ย + ความแปรปรวน (Variance/Dev) ไม่ใช่ Est×2 (ค่าคงที่) ∵ RTT แกว่งมาก Dev ใหญ่ → RTO ขยายเอง
Karn: ไม่วัด SampleRTT จาก seg ที่ retx; timeout → RTO×2 (exp. backoff)
ตย. Est=5,Dev=1,S=7 → Est=5.25 • Dev=.75+.25|7−5.25|=1.1875 → RTO=10.0 (ถ้าใช้ Est เดิม: Dev=1.25, RTO=10.25 — เขียนสูตรกำกับ)
③ RED (Q2) ★★★
AvgLen=(1−w)AvgLen + w·SampleLen
AvgLen < MinTh → P=0 (ผ่าน 100%)
MinTh≤Avg<MaxTh → P = Pmax·(Avg−Min)/(Max−Min)
AvgLen ≥ MaxTh → P=1 (drop 100%)
Throughput% = (1−P)×100 • #drop = N×P
ตย. Min10 Max15: Avg=10→P0 ผ่าน100% | 18→P1 ผ่าน0%
Avg=13: RED-1(Pmax.5)=0.3→70% | RED-2(.7)=0.42→58%
ทำไม AvgLen? กัน burst ชั่วคราว (รถทัวร์เข้าเซเว่น) ไม่ drop เกินเหตุ
ทำไม Random early? กัน Global Synchronization (ทุก flow ลด cwnd พร้อมกัน→link ว่างสลับแน่น) • Drop-tail = ทิ้งเมื่อเต็ม
Pmax สูง → ดรอปเร็ว/แรงกว่า (RED-2 aggressive)
④ DECbit
Router ตั้ง bit เมื่อ avg queue ≥ 1 • Source ดู bit ใน window ก่อน:
<50% set → cwnd+1 | ≥50% → cwnd×0.875
= Congestion Avoidance แบบ router ช่วย (explicit) ↔ RED = implicit (drop)
⑤ Windows & Congestion (Q3)
rwnd (Advertised Window) = ผู้รับบอกพื้นที่ buffer ว่าง → Flow control (กันผู้รับล้น)
cwnd = ผู้ส่งประเมินเอง → Congestion control (กันเครือข่ายล้น)
EffWin = min(rwnd,cwnd) − (LastSent−LastAcked)
Slow Start: เริ่ม cwnd=1 MSS, +1/ACK → ×2 ทุก RTT (exponential) จนถึง ssthresh
Cong. Avoidance: +1 MSS/RTT (linear) — AIMD (Add +1 / Mult ÷2)
Timeout → ssthresh=cwnd/2, cwnd=1 (Tahoe) • 3 dupACK → Fast Retx; Reno: cwnd=ssthresh=cwnd/2 (Fast Recovery)
TCP = reactive (วัวหายล้อมคอก) ต้องเกิด loss ก่อนถึงลด → ทำ CBR ไม่ได้

① 802.11 พื้นฐาน
ทำไม ไม่ใช้ CSMA/CD: (1) สัญญาณตัวเองแรงกลบสัญญาณเข้า → ตรวจชนขณะส่งไม่ได้ (2) Hidden terminal → ใช้ CSMA/CA + ACK

② CSMA/CA + SIFS/DIFS (Q7)
ว่าง DIFS → ส่ง • ไม่ว่าง → สุ่ม backoff, นับถอยเมื่อว่าง, หยุดนับเมื่อไม่ว่าง → 0 แล้วส่ง • ผู้รับรอ SIFS → ACK • ไม่ได้ ACK → backoff เพิ่ม (×2)
ลำดับ: SIFS < PIFS < DIFS (สั้น=สำคัญกว่า)
ทำไม ACK รอ SIFS? ให้ ACK (และ CTS) ได้สิทธิ์ก่อน สถานีอื่นที่ต้องรอ DIFS → ไม่มีใครแทรกชน ACK
ถ้ารอ DIFS? สถานีอื่นอาจส่ง DATA พร้อม ACK → ชน → ผู้ส่งไม่ได้ ACK → ส่ง DATA ทั้งเฟรมซ้ำ เปลือง airtime
③ Hidden vs Exposed Terminal (Q6) ★★★
Hidden: A,C ส่งถึง B แต่ ไม่ได้ยินกันเอง (สิ่งกีดขวาง/ไกล/fading) → ชนที่ B
แก้: RTS/CTS — A ส่ง RTS(สั้น) → B ตอบ CTS ให้ทุกคนได้ยิน (รวม C) → C ตั้ง NAV เงียบตาม Duration → A ส่ง DATA → ACK • ชนได้แค่ RTS สั้น ๆ ไม่เสียมาก
Exposed: S1→R1 กำลังส่ง; S2 ได้ยิน S1 จึง ไม่ยอมส่งไป R2 ทั้งที่ R2 อยู่นอกระยะ S1 → เสียโอกาส (ใช้ช่องไม่คุ้ม)
RTS/CTS ช่วย: S2 ได้ยิน RTS แต่ไม่ได้ยิน CTS ของ R1 → รู้ว่าส่งได้ ไม่รบกวน R1
สรุป: Hidden = ชนเพราะไม่รู้ | Exposed = เงียบโดยไม่จำเป็น

⑤ Mobile IP (Q9) ★★
HA (ตม.ไทย) อยู่ home net • FA (ตม.ลาว) อยู่ visited net • Permanent addr = IP ถาวร • COA = Care-of-Address ที่ visited net
Indirect 6 ขั้น:
1) Mobile เข้า visited → ลงทะเบียนกับ FA ได้ COA
2) FA แจ้ง COA → HA
3) Corresp. ส่งไป permanent addr → ถึง home net
4) HA ดักรับ → encapsulate/tunnel → COA (FA)
5) FA decapsulate → ส่งให้ mobile
6) Mobile ตอบ ตรง ถึง corresp. (src=permanent)
ปัญหา: Triangle routing (อ้อมผ่าน HA แม้อยู่ใกล้กัน)
Direct: corresp. ถาม HA ขอ COA → tunnel ตรงไป FA ✓สั้น ✗ไม่โปร่งใสต่อ corresp., ย้ายเครือข่ายต้องใช้ anchor FA
⑥ Q10 งานพรีเซนต์ (Concept)
ECH: SNI ใน TLS ClientHello เดิมเป็น plaintext → คนกลางรู้เว็บ • ECH แบ่ง Outer CH (SNI สาธารณะ เช่น cloudflare-ech.com) + Inner CH เข้ารหัส (SNI จริง) ด้วย public key จาก DNS HTTPS record • GREASE = ส่ง ECH ปลอมแบบสุ่มเสมอ → middlebox ไม่ ossify/แยกไม่ออก • ข้อเสีย: firewall กรองด้วย SNI ไม่ได้
1D-CNN Jamming (Edge): วัด RSS เป็นอนุกรมเวลา • Constant jammer (AWGN ต่อเนื่อง RSS สูง) acc 100% • Periodic (สลับเงียบ ช่วงเงียบเหมือน normal) 72% • รวม 86.3% บน Raspberry Pi+HackRF • ทำไม Edge: jam แล้ว ต่อ cloud ไม่ได้
IoT DDoS ML: default password → Mirai/Bashlite botnet → C&C สั่ง → Volumetric/Protocol/App DDoS • Signature-based ✗ (traffic ใหม่/หลากหลาย/อุปกรณ์จำกัด) → ML gateway (RF, XGBoost, SVM, KNN) จับ pattern ผิดปกติ

บท 5 Transport Layer — ข้อสังเกต & แนวคิดสำคัญ

5.1 RTT / RTO — หัวใจของ Q1

EstimatedRTT = (1 − α)·EstimatedRTT + α·SampleRTT (α = 0.125 = 1/8) DevRTT = (1 − β)·DevRTT + β·|SampleRTT − EstimatedRTT| (β = 0.25 = 1/4) TimeoutInterval (RTO) = EstimatedRTT + 4·DevRTT
✅ แนวคิดสำคัญ
  • RTO ต้อง มากกว่า RTT เสมอ แต่ไม่มากเกินไป
  • EWMA = ให้น้ำหนักค่าล่าสุดมากกว่าค่าเก่า (ค่าเก่าลดลงแบบ exponential)
  • DevRTT = "margin ความปลอดภัย" ที่ปรับตามความแกว่ง: RTT นิ่ง → margin เล็ก; RTT แกว่ง → margin ใหญ่
  • Karn's algorithm: ไม่เอา SampleRTT ของ segment ที่ถูกส่งซ้ำมาคำนวณ (ไม่รู้ว่า ACK ตอบตัวไหน) + timeout แล้ว RTO ×2
⚠️ กับดัก
  • RTO ต่ำ ≠ "เร็วขึ้น" — แต่ทำให้ Premature Timeout: แพ็กเก็ตยังไม่หาย แต่ส่งซ้ำ → ซ้ำซ้อน + TCP เข้าใจผิดว่าคับคั่ง → ลด cwnd ทั้งที่ไม่จำเป็น
  • RTO สูงเกิน → เมื่อหายจริง ต้องรอนาน (slow recovery) → throughput ตก
  • สูตรเก่า RTO = 2 × EstimatedRTT ใช้ตัวคูณคงที่ ไม่สะท้อนความแปรปรวน → RTT แกว่งมาก ๆ ก็ยัง timeout ผิด

5.2 RED (Random Early Detection) — หัวใจของ Q2

ถ้า AvgLen < MinTh → P_drop = 0 ถ้า MinTh ≤ AvgLen < MaxTh → P_drop = Pmax × (AvgLen − MinTh) / (MaxTh − MinTh) ถ้า AvgLen ≥ MaxTh → P_drop = 1 P_Throughput = (1 − P_drop) × 100% จำนวนที่ผ่าน = N × (1 − P_drop)
✅ แนวคิดสำคัญ
  • RED = router ทิ้งแพ็กเก็ตแบบสุ่มก่อนคิวเต็ม เพื่อ "ส่งสัญญาณเตือน" TCP ให้ลด cwnd ตั้งแต่เนิ่น ๆ (implicit notification)
  • ใช้ ค่าเฉลี่ยคิว (AvgLen, EWMA) ไม่ใช่ค่าทันที → ทน burst สั้น ๆ ได้ (ตัวอย่างอาจารย์: รถทัวร์เข้าเซเว่น คนแน่นแป๊บเดียว ไม่ต้องปิดร้าน)
  • สุ่มทิ้ง → แต่ละ flow ลด cwnd ไม่พร้อมกัน → กัน Global Synchronization
  • ทิ้งตามสัดส่วน → flow ที่ส่งเยอะโดนทิ้งเยอะ (ยุติธรรมขึ้น)
⚠️ กับดัก
  • โจทย์ถาม Throughput หรือ Drop? อ่านให้ดี! (Pdrop=0.3 → Throughput=70%)
  • ค่า AvgLen = MinTh พอดี → P=0 (ยังไม่ทิ้ง) • AvgLen ≥ MaxTh → ทิ้ง 100% (ไม่ใช่ Pmax!)
  • Pmax คือค่าที่ MaxTh ไม่ใช่ค่าสูงสุดของกราฟ (กราฟกระโดดเป็น 1 หลัง MaxTh)
  • เขียน สูตร + แทนค่า + ผลลัพธ์ ทุกครั้ง เผื่อได้คะแนนวิธีทำ

5.3 Flow vs Congestion Control (Q3)

เรื่องFlow ControlCongestion Control

ตัวแปรrwnd (Advertised Window) — ผู้รับส่งมาใน headercwnd — ผู้ส่งคำนวณเอง

💡 ไล่ค่า cwnd (เผื่อออก) ssthresh = 16: cwnd = 1 → 2 → 4 → 8 → 16 (slow start ×2) → 17 → 18 → 19 (avoidance +1) → timeout: ssthresh = 19/2 ≈ 9, cwnd = 1 (Tahoe) • หรือ 3 dup ACK (Reno): cwnd = 9 แล้ว +1 ต่อ RTT

บท 6 Application Layer & IoT — ข้อสังเกต & แนวคิดสำคัญ

6.1 DNS

  • ทำงานบน UDP port 53 (เร็ว, query เล็ก) — TCP เฉพาะ response ใหญ่/zone transfer
  • ลำดับชั้น: Local DNS → Root → TLD (.com/.th) → Authoritative
  • Iterative (local ไล่ถามเอง) vs Recursive (ส่งต่อให้คนถัดไปถามแทน) • Cache ตาม TTL
  • Record: A, AAAA, MX, CNAME, NS, HTTPS (ใช้กับ ECH)

6.2 Email

  • SMTP (25) = push ส่งจาก UA → mail server และ server → server
  • POP3 (110) = pull, download-and-delete, ไม่ sync
  • IMAP (143) = pull, เก็บบน server, sync หลายอุปกรณ์
  • ทั้งหมดใช้ TCP (ต้องเชื่อถือได้)

6.3 DASH & CDN

  • Server เก็บวิดีโอหลาย bitrate ตัดเป็น chunk
  • Manifest file (MPD) = "เมนู" บอก URL ของ chunk แต่ละ bitrate → client โหลดก่อนเป็นอันดับแรก
  • Client ฉลาด: วัด bandwidth / buffer แล้วเลือก bitrate ทีละ chunk → ภาพไม่ค้าง (คุณภาพลดแทน)
  • Server = HTTP server ธรรมดา ไม่ต้องเก็บ state → scale ง่าย + ใช้ CDN ได้
  • CDN: Enter Deep (Akamai วาง server ลึกใน ISP จำนวนมาก ใกล้ user) vs Bring Home (Limelight คลัสเตอร์ใหญ่ไม่กี่จุดที่ IXP ดูแลง่าย)

6.4 MQTT vs CoAP

  • MQTT: TCP, Publish/Subscribe ผ่าน Broker, topic, header 2 bytes, QoS 0/1/2
  • CoAP: UDP, Request/Response แบบ REST, response code เช่น 2.05 Content, CON/NON
⚠️ กับดัก True/False ที่อาจารย์ชอบ
  • "POP3 ใช้ส่งอีเมล" → ผิด (SMTP ส่ง, POP3 ดึง)
  • "Email ใช้ UDP เพื่อความเร็ว" → ผิด (TCP)
  • "CoAP ทำงานบน TCP เหมือน HTTP" → ผิด (UDP) • "MQTT ใช้ UDP" → ผิด (TCP)
  • "MQTT QoS 1 รับประกันว่าได้รับครั้งเดียว" → ผิด (at least once อาจซ้ำ; exactly once = QoS 2)
  • "MQTT client คุยกันโดยตรง" → ผิด (ผ่าน Broker; publisher/subscriber ไม่รู้จักกัน = decoupled)
  • "DASH ให้ server เป็นผู้เลือก bitrate" → ผิด (client เลือก)
  • "DNS ใช้ TCP 53 เป็นหลัก" → ผิด (UDP เป็นหลัก) • "HTTP/3 ใช้ TCP" → ผิด (QUIC/UDP)

Q3 (2 คะแนน) อธิบาย Advertised Window และ Slow Start
Advertised Window (rwnd): ขนาดพื้นที่ว่างใน receive buffer ที่ผู้รับแจ้งกลับใน TCP header → ผู้ส่งห้ามส่งข้อมูลค้าง ACK เกิน rwnd (Flow control)
Slow Start: ช่วงเริ่มต้น/หลัง timeout ตั้ง cwnd = 1 MSS แล้วเพิ่ม 1 MSS ต่อ ACK → cwnd เพิ่มเป็น 2 เท่าทุก RTT จนถึง ssthresh หรือเกิด loss
Q4 (2 คะแนน) ถูก/ผิด เกี่ยวกับ MQTT, CoAP, SMTP/POP3, Email
หลักจำ: MQTT = TCP + Pub/Sub + Broker + QoS 0/1/2 • CoAP = UDP + REST Req/Resp • SMTP ส่ง / POP3-IMAP ดึง • Email ทุกตัวใช้ TCP — ข้อความใดขัดกับหลักนี้ = ผิด
Q5 (3 คะแนน) Manifest File ใน DASH คืออะไร มีบทบาทอย่างไร
ไฟล์ที่ server ให้ client โหลดเป็นอันดับแรก ระบุ รายการ chunk ของวิดีโอในแต่ละ bitrate/ความละเอียดพร้อม URL → client ใช้วัด bandwidth ที่มีแล้ว เลือก bitrate ที่เหมาะสมทีละ chunk (adaptive) ทำให้ดูได้ลื่นไม่ค้าง และ server ไม่ต้องตัดสินใจแทน (ใช้ HTTP server/CDN ธรรมดาได้)
Q6 (3 คะแนน) Hidden Terminal Problem คืออะไร และ แก้อย่างไร
ปัญหา: A และ C อยู่ในระยะของ B แต่ ไม่ได้ยินสัญญาณกันเอง (ไกล/มีสิ่งกีดขวาง/fading) → carrier sense แล้วคิดว่าว่าง ส่งพร้อมกัน → ชนที่ B
วิธีแก้ RTS/CTS: A ส่ง RTS สั้น ๆ → B ตอบ CTS ซึ่งทุกสถานีรอบ B (รวม C) ได้ยิน → C ตั้ง NAV งดส่งตาม duration → A ส่ง DATA ได้ไม่ชน (ถ้าชนก็ชนแค่ RTS สั้น ๆ)
Q7 (2 คะแนน) ทำไมผู้รับรอ SIFS ก่อนส่ง ACK ไม่ใช่ DIFS
SIFS สั้นกว่า DIFS → ACK ได้ สิทธิ์ใช้ช่องก่อน สถานีอื่นที่ต้องรอ DIFS ก่อนเริ่มส่ง → ไม่มีใครแทรกส่งชน ACK; ถ้ารอ DIFS ACK อาจชนกับเฟรมใหม่ ผู้ส่งไม่ได้ ACK ต้องส่ง DATA ทั้งเฟรมซ้ำ
Q8 (2 คะแนน) ความแตกต่างระหว่าง 3G และ 4G
3G: core แยก 2 ส่วน — เสียงใช้ circuit-switched (MSC), ข้อมูลใช้ packet-switched (SGSN/GGSN), WCDMA
4G: All-IP packet-switched ทั้งหมด (เสียงเป็น VoLTE) core เดียว (EPC), OFDMA → เร็วกว่า latency ต่ำกว่า
Q9 (3 คะแนน) เรียงลำดับ Mobile IP Indirect Routing
① Mobile ลงทะเบียนกับ FA ได้ COA → ② FA แจ้ง COA ให้ HA → ③ Correspondent ส่งไป permanent address ถึง home network → ④ HA ดักรับแล้ว encapsulate (tunnel) ไปยัง COA → ⑤ FA decapsulate ส่งให้ mobile → ⑥ Mobile ตอบกลับ correspondent โดยตรง

Q1 แบบพลิก — RTT/RTO สูงมาก

1A. กำหนด EstimatedRTT = 5 ms, DevRTT = 1 ms, SampleRTT ใหม่ = 7 ms (α = 0.125, β = 0.25) จงหา RTO ใหม่
Est = 0.875×5 + 0.125×7 = 5.25 ms • Dev = 0.75×1 + 0.25×|7 − 5.25| = 0.75 + 0.4375 = 1.1875 ms • RTO = 5.25 + 4×1.1875 = 10.0 ms
(ถ้าใช้ Est เดิม (5) คำนวณส่วนต่างตามแบบ Jacobson: Dev = 0.75 + 0.5 = 1.25 → RTO = 10.25 ms — เขียนสูตรที่ใช้กำกับไว้ อาจารย์ให้คะแนนตามวิธีทำ)
1B. ทำไม RTO = 2 × EstimatedRTT จึงไม่ดีเท่า Est + 4·DevRTT
ตัวคูณคงที่ไม่สนความแปรปรวน: RTT นิ่ง → margin ใหญ่เกิน (กู้ช้า), RTT แกว่ง → margin เล็กเกิน (timeout ผิด) • DevRTT ปรับ margin อัตโนมัติตามความแกว่งจริง
1C. ถ้ากราฟ RTT แกว่งมาก (2–20 ms) จะตั้ง RTO = 10 ms ดีไหม
ไม่ดี — ช่วงที่ RTT > 10 จะ timeout ก่อนเวลา ส่งซ้ำไม่จำเป็น; ความแปรปรวนสูง DevRTT ใหญ่ → RTO ควรสูงกว่าค่าสูงสุดที่พบบ่อย

2F. DECbit: ใน window ก่อนหน้า 10 แพ็กเก็ต มี bit ถูกตั้ง 6 ตัว cwnd = 16 → cwnd ใหม่?
60% ≥ 50% → ลดแบบ multiplicative: 16×0.875 = 14 (ถ้า < 50% → 17)

Q3 แบบพลิก — TCP Window สูง

3A. Congestion Window ต่างจาก Advertised Window อย่างไร ผู้ส่งใช้ค่าใด
rwnd = ผู้รับกำหนด (กันผู้รับล้น), cwnd = ผู้ส่งประเมิน (กันเครือข่ายล้น) • ส่งได้ไม่เกิน min(rwnd, cwnd)
3B. อธิบาย Congestion Avoidance / AIMD
หลัง cwnd ≥ ssthresh เพิ่มแบบเส้นตรง +1 MSS ต่อ RTT (Additive Increase) • เมื่อเกิด loss ลด cwnd ครึ่งหนึ่ง (Multiplicative Decrease) → กราฟฟันเลื่อย, แบ่ง bandwidth อย่างยุติธรรม
3C. Timeout กับ 3 Duplicate ACK ต่างกันอย่างไร
Timeout = รุนแรง (ไม่มีอะไรผ่านเลย) → cwnd = 1 เริ่ม slow start ใหม่ • 3 dup ACK = ยังมีแพ็กเก็ตผ่าน หายแค่ตัวเดียว → Fast Retransmit + (Reno) ลด cwnd ครึ่งเดียว Fast Recovery

Q4 แบบพลิก — ถูก/ผิด Application/IoT สูง

4A. ตัดสินถูก/ผิด: (1) IMAP เก็บอีเมลบน server และ sync ได้หลายอุปกรณ์ (2) DNS query ปกติใช้ UDP 53 (3) MQTT QoS 0 รับประกันการส่งถึง (4) CoAP ใช้ GET/PUT/POST/DELETE (5) P2P ขยายตัวได้เองเมื่อมี peer เพิ่ม
(1) ถูก (2) ถูก (3) ผิด — at most once ไม่รับประกัน (4) ถูก (5) ถูก (self-scalability)

Q5 แบบพลิก — Streaming/CDN กลาง-สูง

5A. ใน DASH "ความฉลาด" อยู่ที่ฝั่งใด เพราะอะไร
ฝั่ง Client — client รู้สภาพเครือข่าย/buffer ของตัวเองดีที่สุด จึงเลือก bitrate และเวลาที่จะขอ chunk เอง → server เบา, stateless, ใช้ CDN ได้
5B. ทำไมไม่ใช้ Mega Server เดียว และ CDN มีแนวทางอะไรบ้าง
Mega server: single point of failure, ไกลจาก user (delay), คอขวด link, ส่งซ้ำ ๆ เปลือง → CDN กระจายสำเนาใกล้ผู้ใช้: Enter Deep (Akamai เข้าลึกใน access ISP จำนวนมาก) vs Bring Home (คลัสเตอร์ใหญ่ไม่กี่จุดใกล้ IXP ดูแลง่าย)

Q6 แบบพลิก — 802.11 สูงมาก

6A. Exposed Terminal Problem คืออะไร และ RTS/CTS ช่วยอย่างไร
S1 กำลังส่งให้ R1; S2 อยู่ในระยะ S1 ได้ยินสัญญาณจึงงดส่งไป R2 ทั้งที่ R2 อยู่นอกระยะ S1 (ส่งได้ไม่รบกวน) → เสียโอกาสใช้ช่องสัญญาณ • RTS/CTS: S2 ได้ยิน RTS ของ S1 แต่ ไม่ได้ยิน CTS จาก R1 → รู้ว่าตนไม่ได้อยู่ใกล้ผู้รับ ส่งได้
6B. ทำไม 802.11 ไม่ใช้ CSMA/CD เหมือน Ethernet
(1) ขณะส่ง สัญญาณของตัวเองแรงกว่าสัญญาณที่รับมาก ตรวจจับการชนไม่ได้ (half-duplex radio) (2) Hidden terminal/fading ทำให้ผู้ส่งไม่เห็นการชนที่เกิดที่ผู้รับ → ใช้ CSMA/CA (หลีกเลี่ยง) + ACK แทน
6C. Passive vs Active Scanning
Passive: AP ส่ง Beacon เป็นระยะ host ฟังแล้วเลือก AP • Active: host broadcast Probe Request, AP ตอบ Probe Response → จากนั้น Association Request/Response

Q7 แบบพลิก — Interframe Space กลาง

7A. ถ้าผู้รับรอ DIFS ก่อนส่ง ACK จะเกิดอะไร / เรียงลำดับ SIFS, PIFS, DIFS
สถานีอื่นที่รอ DIFS เช่นกันอาจเริ่มส่งพร้อม ACK → ชน → ผู้ส่งไม่ได้ ACK → timeout ส่ง DATA ซ้ำทั้งเฟรม • SIFS < PIFS < DIFS
7B. NAV คืออะไร
Network Allocation Vector — ตัวจับเวลาที่สถานีตั้งจากฟิลด์ Duration ใน RTS/CTS/DATA เพื่อ "จองช่อง" งดส่งจนกว่าการรับส่งของคนอื่นจบ (virtual carrier sensing)

Q8 แบบพลิก — Cellular สูง

8A. 1G ต่างจาก 2G อย่างไร
1G analog เสียงอย่างเดียว FDMA, BS ต่อ MSC ตรง • 2G digital (เสียง+SMS) เพิ่ม BSC ควบคุมหลาย BS, GSM ใช้ FDMA+TDMA / IS-95 ใช้ CDMA, รองรับ handoff/paging ดีขึ้น
8B. 2G ต่างจาก 3G อย่างไร
2G core เป็น circuit-switched (เสียงเป็นหลัก) • 3G เพิ่ม packet core (SGSN/GGSN) สำหรับข้อมูลความเร็วสูง ขนานกับ circuit core เดิม, ใช้ WCDMA
8C. 5G มี use case หลักอะไร
eMBB (บรอดแบนด์เร็วมาก เช่น วิดีโอ 4K/VR) • URLLC (หน่วงต่ำ เชื่อถือได้สูง เช่น รถไร้คนขับ/ผ่าตัดระยะไกล) • mMTC (อุปกรณ์ IoT จำนวนมหาศาล) + network slicing

Q9 แบบพลิก — Mobile IP สูง

9A. Direct Routing ต่างจาก Indirect Routing อย่างไร แก้ปัญหาอะไร
Indirect: correspondent ส่งไป HA → tunnel ไป FA (อ้อม = Triangle Routing) • Direct: correspondent agent ขอ COA จาก HA แล้ว tunnel ตรงไป FA → เส้นทางสั้นกว่า แต่ไม่โปร่งใส (correspondent ต้องรู้ COA) และถ้า mobile ย้ายต่อต้องใช้ anchor FA
9B. อธิบายบทบาท HA, FA, Permanent Address, COA
HA = router ใน home network รับแทนและ tunnel ต่อ (ตม.ไทยที่รู้ว่าคนไทยไปอยู่ไหน) • FA = router ใน visited network ให้ COA และส่งต่อให้ mobile (ตม.ลาว) • Permanent = IP ถาวรที่คนอื่นใช้ติดต่อ • COA = ที่อยู่ชั่วคราวใน visited network

Q10 (ซ่อน! CLO 3) — งานที่เพื่อนพรีเซนต์ สูง (Concept)

10A. ECH (Encrypted Client Hello) แก้ปัญหาอะไร ทำงานอย่างไร
ปัญหา: SNI ใน TLS ClientHello ส่งแบบ plaintext → ISP/คนกลางรู้ว่าเข้าเว็บใดแม้ใช้ HTTPS • ECH แบ่ง Outer ClientHello (SNI สาธารณะของ CDN) กับ Inner ClientHello ที่เข้ารหัส (SNI จริง) ด้วย public key ที่ได้จาก DNS HTTPS record
10B. GREASE ใน ECH คืออะไร / ECH มีผลกระทบด้านความปลอดภัยองค์กรอย่างไร
GREASE = client ส่ง ECH ปลอมแบบสุ่มแม้ไม่ได้ใช้จริง → middlebox แยกไม่ออก และไม่ "ossify" (ไม่ hard-code บล็อก extension ใหม่) • ผลกระทบ: firewall/content filter กรองด้วย SNI ไม่ได้ ต้องใช้วิธีอื่น (DNS policy, endpoint agent)
10C. ทำไมตรวจจับ Jamming บน Edge ด้วย 1D-CNN และทำไม Periodic jammer ตรวจยากกว่า
เมื่อถูก jam อุปกรณ์ส่งข้อมูลไป cloud ไม่ได้ จึงต้องตัดสินใจที่ edge (Raspberry Pi) • 1D-CNN เหมาะกับข้อมูลอนุกรมเวลา RSS • Constant jammer ส่ง noise ต่อเนื่อง RSS สูงตลอด → แม่น 100% • Periodic สลับส่ง/เงียบ ช่วงเงียบดูเหมือน normal → แม่นแค่ ~72% (รวม 86.3%)
10D. ทำไม IoT ตกเป็น Botnet ง่าย และทำไมใช้ ML แทน Signature-based
IoT ใช้ default password, ไม่ค่อย update, ทรัพยากรน้อย → Mirai/Bashlite สแกนยึดเครื่อง รับคำสั่งจาก C&C ยิง DDoS (Volumetric/Protocol/Application) • Signature-based จับได้แค่ที่รู้จัก traffic IoT หลากหลาย/ปรับเปลี่ยนเร็ว → ML (Random Forest, XGBoost, SVM, KNN) ที่ gateway เรียนรู้รูปแบบผิดปกติได้ รวมถึงการโจมตีใหม่
