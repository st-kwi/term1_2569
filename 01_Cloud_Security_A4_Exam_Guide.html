1. S6: Threat, Vulnerability, Risk & KEV/CVE/CVSS ออกสอบเน้น!
  • Asset (สินทรัพย์): สิ่งที่มีคุณค่าต่อองค์กร (Data, App, IAM Role, Cloud Account, ชื่อเสียง)
  • Threat (ภัยคุกคาม): เหตุการณ์หรือผู้กระทำที่อาจสร้างความเสียหาย (Attacker, Bot, ภัยธรรมชาติ)
  • Vulnerability (ช่องโหว่): จุดอ่อนที่ทำให้ Threat เจาะสำเร็จ แบ่งเป็น 3 เสาหลัก: Technical Flaw, Process Flaw, Human & Identity Flaw และ 4 ประเภท: Configuration, Software, Identity, Design
  • Attack Vector (ช่องทางโจมตี): เส้นทางที่ผู้โจมตีใช้เข้าถึงเป้าหมาย (เช่น Public Bucket, Leaked Key, Phishing, API)
  • Risk (ความเสี่ยง): โอกาสเกิดความเสียหายต่อธุรกิจเมื่อ Threat ใช้ Vulnerability โจมตี Asset จนเกิด Impact

(Common Vulnerabilities & Exposures)		รหัสมาตรฐานสากลสำหรับระบุชื่อช่องโหว่ (เช่น CVE-2024-XXXX) ใช้คุยอ้างอิงให้ตรงกัน (ไม่ได้บอกคะแนนความเสี่ยง)
CVSS
(Common Vulnerability Scoring System)		คะแนนความรุนแรงทางเทคนิค (0.0–10.0) วัดความยากง่ายในการเจาะและผลกระทบเชิงเทคนิค แต่ยังไม่รวมบริบทธุรกิจ
CISA KEV
(Known Exploited Vulnerabilities)		บัญชีรายชื่อช่องโหว่ที่มีหลักฐานยืนยันว่าถูกโจมตีจริงแล้วในโลกจริง (Active Exploitation) จัดทำโดย CISA → ใช้เป็นตัวเร่ง (Accelerator) ที่ต้องรีบ Patch ด่วนที่สุด!
Contextual Risk & ISAR / DBIR / ASPM• Contextual Risk = CVSS + Business Context (Asset Criticality, Data Sensitivity, Compensating Controls)
• ISAR / CISA / DBIR / BIS: รายงานวิเคราะห์อุบัติการณ์และรูปแบบการเจาะระบบจริง

2. S6: 4 ภัยคุกคามหลักบนคลาวด์ (4 Cloud Threats) & วงจรช่องโหว่ Case Study
ภัยคุกคาม (Threat)จุดอ่อนหลัก / ลักษณะอาการ (Evidence)CIAControl แรกที่ต้องทำทันที
1. Misconfiguration
(ตั้งค่าผิดพลาด)		 3 มิติอันตราย: Public + Privileged + Unmonitored
4 จุดเสี่ยง: Storage (Public S3), Network (0.0.0.0/0), Permissions (IAM *), Visibility (ไม่เปิด Log)		 C / I Close exposure: เปิด Block Public Access, จำกัด Security Group, ใช้ Guardrails
2. Credential Leakage
(ข้อมูลยืนยันตัวตนรั่ว)		 3 เฟส: Source (เผลอฝัง Key ใน Git/Code/Log) → Bypass (ข้าม MFA เข้า API) → Infiltration (ใช้สิทธิ์ Role ยึดระบบ) C / I Revoke & Rotate Key ทันที + บังคับ MFA + ใช้ Short-lived Role + ตรวจ Historical Logs ย้อนหลัง!
3. Insecure APIs
(API ไม่ปลอดภัย)		 • BOLA (Broken Object Level AuthZ): แก้เลข ID ใน URL แล้วดูข้อมูลคนอื่นได้
• Function-level flaw: User ธรรมดาเรียกคำสั่ง Admin ได้
• ส่งคอลัมน์ข้อมูลกลับมามากเกินจำเป็น (Excessive Data)		 C Fix AuthZ 3 ระดับ (Identity, Resource, App), ทำ Rate Limit, Schema Validation, ทดสอบ Negative Case
4. Data Exposure
(ข้อมูลรั่วไหล)		 4 ช่องทาง: Storage เปิดสาธารณะ, แชร์ Backup/Snapshot ออกนอกองค์กร, KMS Policy หละหลวม, ยอด Bulk Download พุ่ง C Restrict Access: ยกเลิก Public Link/Signed URL, ตั้งค่า DLP, เข้ารหัสและจำกัดสิทธิ์ KMS
Vulnerability Lifecycle (4 ขั้นตอน): 1. Discover (ค้นหาด้วย Scan/Inventory/Threat Intel) → 2. Triage (คัดกรองความจริง + ประเมินความรุนแรงตามบริบท + ตั้ง Owner/Due Date) → 3. Remediate (แก้ไข: Patch / Reconfigure / Isolate / Compensating Control) → 4. Verify (สแกนซ้ำ Rescan & ตรวจ Log ยืนยันว่าหายจริง)

• Attack Chain 5 ขั้นเมื่อ Key หลุด: 1. Key leak → 2. API access → 3. Role abuse → 4. Storage read → 5. Data loss

• Patch & Dependency Pipeline (Change Mgmt): Commit (ทำ Asset Inventory) → Build (สแกน Container/IaC/SCA ใน CI/CD) → Stage (กำหนด Patch SLA ตาม Severity/KEV, ทดสอบใน Staging + มี Rollback Plan เสมอ) → Prod (ทยอย Rollout)

3. S6: Control Level Impact, Risk Matrix & การจัดการความเสี่ยง หัวข้อเน้นสอบ!
สมการความเสี่ยง: Risk Score = Likelihood (โอกาสเกิด 1–5) × Impact (ผลกระทบ 1–5) (คะแนนเต็ม 25)
  • Likelihood (1–5): 1 = Rare, 2 = Unlikely, 3 = Possible, 4 = Likely, 5 = Almost Certain (ดูจาก Exposure, Exploitability/KEV, Threat Activity, Control ที่มี)
  • Impact (1–5): 1 = Negligible, 2 = Minor, 3 = Moderate, 4 = Major, 5 = Severe (ดูจาก CIA Triad, มูลค่าข้อมูล PII, ระบบธุรกิจหยุดชะงัก, ค่าปรับกฎหมาย PDPA/GDPR)
คะแนน (L×I)ระดับความเสี่ยงแนวทางปฏิบัติในองค์กร (Organizational Action)
17 – 25Critical (วิกฤต)Escalate ผู้บริหารทันที + เปิดกระบวนการ Incident Response / แก้ไขฉุกเฉินทันที
10 – 16High (สูง)Urgent Mitigation: ลดความเสี่ยงอย่างเร่งด่วน กำหนดแผนแก้ไขและติดตามผลใกล้ชิด
5 – 9Medium (ปานกลาง)กำหนด Owner (ผู้รับผิดชอบ) และ Due Date (กำหนดเสร็จ) ชัดเจนในแผนงานปกติ
1 – 4Low (ต่ำ)Monitor: เฝ้าระวังและแก้ไขตามรอบการบำรุงรักษาระบบตามปกติ

• ตัวเร่งลำดับความสำคัญ (Accelerators): 1. Exploit Evidence (อยู่ใน CISA KEV) และ 2. Regulatory Deadline (เส้นตายกฎหมาย) | ตัวตัดสินเมื่อคะแนนเท่ากัน (Tie-breakers): ดู Asset Criticality หรือเลือกข้อที่เป็น Quick Win (ทำง่ายลดเสี่ยงได้ทันที)

Control Level Impact (ผลของ Control ต่อการลด Likelihood vs ลด Impact)
ประเภท Controlเป้าหมายตัวอย่างการนำไปใช้ในองค์กร
1. Preventive Control
(ลดค่า Likelihood - L)		ลดโอกาสที่ผู้โจมตีจะเจาะเข้ามาสำเร็จการเปิด MFA, Block Public Access, Key Rotation, Least Privilege IAM, Patching, WAF บล็อก SQLi
2. Containment / Recovery
(ลดค่า Impact - I)		จำกัดวงความเสียหาย (ลด Blast Radius) และกู้คืนไวการทำ Micro-segmentation, Immutable Backup (WORM), Multi-AZ Failover, Encryption at Rest
  • Inherent Risk (ความเสี่ยงตั้งต้น): ความเสี่ยงก่อนใส่ Control (เช่น Bucket เปิด Public + มี PII: L4 × I5 = 20 [Critical])
  • Residual Risk (ความเสี่ยงหลงเหลือ): ความเสี่ยงที่เหลืออยู่หลังจากใส่ Control แล้ว (เช่น ปิด Public + บังคับ MFA ทำให้โอกาสเกิดลดลงเหลือ L2: L2 × I5 = 10 [High/Medium])
  • Compensating Control (การควบคุมชดเชย): มาตรการทดแทนชั่วคราวเมื่อยังไม่สามารถแก้ที่ต้นเหตุ (Root Cause) ได้ทันที เช่น แอป Legacy ยัง Patch ช่องโหว่ไม่ได้ จึงตั้งกฎ AWS WAF (Virtual Patching) หรือจำกัด IP Whitelist กั้นหน้าไว้ก่อน
4 กลยุทธ์การจัดการความเสี่ยง (4 Risk Management Decisions) — ออกสอบเน้น!
กลยุทธ์ความหมายและการประยุกต์ใช้ในองค์กร
1. Avoid
(หลีกเลี่ยง)		ยกเลิกกิจกรรม/ฟีเจอร์ หรือปิดระบบที่ก่อให้เกิดความเสี่ยงนั้นโดยสิ้นเชิง เมื่อความเสี่ยงสูงเกินรับได้และไม่คุ้มค่าธุรกิจ (เช่น ปิด Public API ที่ไม่ใช้แล้ว, ยกเลิกการเก็บข้อมูลบัตรเครดิตลูกค้าเอง)
2. Mitigate
(ลดความเสี่ยง)		เพิ่มมาตรการควบคุม (Security Controls) เพื่อลดโอกาสเกิด (L) หรือลดผลกระทบ (I) ให้อยู่ในระดับที่ยอมรับได้ (เช่น เปิด MFA, เข้ารหัส KMS, ตั้งค่า Auto Scaling + WAF)
3. Transfer
(โอนย้ายความเสี่ยง)		ถ่ายโอนภาระความเสียหายทางการเงินหรือการดำเนินงานให้บุคคลที่สาม (Third Party) เช่น การทำประกันภัยไซเบอร์ (Cyber Insurance) หรือใช้บริการ Cloud Managed Service / SaaS ที่มี SLA ชัดเจน (*หมายเหตุ: โอนความรับผิดชอบด้านกฎหมาย/ชื่อเสียงไม่ได้!)
4. Accept
(ยอมรับความเสี่ยง)		ยอมรับความเสี่ยงที่หลงเหลือ (Residual Risk) เมื่ออยู่ในเกณฑ์ Risk Appetite หรือต้นทุนการแก้ไขแพงกว่าความเสียหาย กฎเหล็ก: ต้องมีผู้บริหารลงนามอนุมัติ (Formal Sign-off), ระบุ Owner และวันทบทวน (Review Date)
NIST CSF 1.1 (5 Functions) & กฎเหล็กการวิเคราะห์สู่ Risk Register

• 5 ฟังก์ชัน NIST CSF 1.1: 1. Identify (Pre-incident: รู้ Asset, Owner, Sensitivity) → 2. Protect (Pre-incident: ป้องกันที่ Root Cause แบบ Defense in Depth) → 3. Detect (Visibility: Event → Signal → Alert → Owner → Triage; ระวัง Detection Gap ทำ Impact พุ่ง) → 4. Respond (Post-incident: จำกัด Blast Radius, Revoke key; ต้อง Preserve Evidence เก็บหลักฐานก่อนแก้ระบบเสมอ!) → 5. Recover (Post-incident: กู้คืนระบบ, ลบ Backdoor, อัปเดตบทเรียนเข้า Risk Register)

• กฎแยกแยะหลักฐาน: แยก Observed Fact (สิ่งที่เห็นจริง เช่น Key หลุดใน Git + มี API จากต่างแดน) ออกจาก Hypothesis/Assumption (สมมติฐานว่าข้อมูลรั่ว) แล้วทำ Verification (ตรวจ Log ว่าเข้าถึงถังเก็บ PII หรือไม่)

• สมการ Risk Register: [Threat Analysis] + [CSF Control] + (L × I) = [Risk Register] (ต้องระบุ Owner, Due Date, Measure เพื่อเปลี่ยนความเสี่ยงให้เป็น Action)

4. S7: Data Classification, Data Protection & Data Lifecycle หัวข้อเน้นสอบ!

Cloud Security Blueprint (6 ชั้น): 1. Data Classification → 2. Storage Access → 3. Envelope Encryption → 4. KMS → 5. Secrets Mgmt → 6. Audit & Compliance

3 ขั้นตอนจำแนกข้อมูล: 1. กำหนดระดับอ่อนไหว (Sensitivity) → 2. กำหนดเกณฑ์ประเมิน (Template/Metric) → 3. ร่างนโยบายและติดป้ายกำกับ (Classification Label)

ระดับ (4 / 5 Levels)ความเสี่ยง / การเข้าถึงตัวอย่างข้อมูล & Security Controls ที่ต้องใช้
1. Public
(Level 0: None)		ไม่มีความเสี่ยง / เปิดให้ทุกคนเข้าถึงได้ข่าว PR, หน้าเว็บบริษัท → ไม่ต้องเข้ารหัส (No encryption needed) แต่ต้องรักษา Integrity & Availability
2. Internal
(Level 1: Low)		ความเสี่ยงต่ำ / เฉพาะพนักงานภายในประกาศภายใน, ข้อมูลการตลาด/จัดซื้อทั่วไป → จำกัดสิทธิ์เฉพาะพนักงานองค์กร
3. Confidential (L2)
& Highly Conf. (L3)		ความเสี่ยงปานกลาง-สูง / เฉพาะผู้เกี่ยวข้อง (Need-to-know)งบการเงิน, สัญญา NDA, ข้อมูลลูกค้า/พนักงาน → ต้องมี IAM, Encryption at Rest, Logging
4. Restricted / Secret
(Level 4: Extreme)		ความเสี่ยงสูงสุด (กระทบกฎหมาย/ล้มละลาย) / เฉพาะ Data Owner / ผู้บริหารระดับสูงข้อมูลส่วนบุคคลอ่อนไหว (PII/PDPA), บัตรเครดิต (PCI-DSS), ประวัติการแพทย์, รหัสผ่าน DB → ต้องใช้ Secret Vault, Rotation, Strict Access, Continuous Audit
การปกป้องข้อมูลใน 3 สถานะ (Securing the 3 States of Data)
สถานะข้อมูล (State)ความหมาย / ตัวอย่างมาตรการป้องกัน (Data Protection Controls)
1. Data at Rest
(ข้อมูลที่จัดเก็บนิ่งๆ)		ไฟล์ใน Disk, S3, EBS, RDS, Backup, Archive• SSE-S3 (AWS จัดการคีย์ให้), SSE-KMS (ลูกค้าคุมคีย์+มี Audit Trail), Client-Side Encryption (เข้ารหัสก่อนส่งขึ้นคลาวด์)
• Full Disk / File / DB Encryption, DLP, CASB
2. Data in Transit
(Data in Motion)		ข้อมูลกำลังวิ่งผ่านเครือข่าย (API, Email, Download)• TLS 1.2+ / HTTPS, VPN / IPsec, Email Encryption, Managed File Transfer
3. Data in Use
(ข้อมูลกำลังประมวลผล)		ข้อมูลถูกเปิดอ่าน/แก้ไขอยู่ใน RAM / CPU• RBAC (Role-Based Access Control), Identity Mgmt, DRM, Confidential Computing
วงจรชีวิตข้อมูล 6 ขั้นตอน (6-Stage Data Lifecycle Management)
1. Create (สร้าง) → 2. Store (จัดเก็บ) → 3. Use (ใช้ประมวลผล) → 4. Publish / Share (เผยแพร่/แลกเปลี่ยน) → 5. Archive / Achieve (เก็บถาวรระยะยาว ไม่แก้ไข เช่น Glacier) → 6. Destroy (ทำลายเมื่อหมดอายุการใช้งาน)
Cloud Storage Types & กฎการประเมินสิทธิ์ (Access Control Priority)
  • ประเภท Storage: Object (S3: เก็บไฟล์+Metadata ทนทาน 11 Nines 99.999999999%), File (EFS/FSx: แชร์ไฟล์ NFS/SMB), Block (EBS: ต่อเข้า EC2 ความเร็วสูง IOPS สูงสำหรับ DB), Cold/Archive (Glacier: เก็บระยะยาวราคาถูก), AWS Storage Gateway (เชื่อม On-prem 3 แบบ: File, Volume, Tape Gateway มี Local SSD Cache)
  • ลำดับการตัดสินสิทธิ์ (Policy Priority): 1. EXPLICIT DENY (ชนะทุกสิ่ง!) → 2. EXPLICIT ALLOW → 3. IMPLICIT DENY (ค่าเริ่มต้นคือบล็อกทั้งหมด Private by Default)
  • 3 เสาหลักควบคุมสิทธิ์ S3: 1. IAM Policy (ใครทำอะไรได้) + 2. Bucket Policy & Block Public Access (เข้าถึงถังนี้จากไหนได้) + 3. KMS Key Policy (ใครมีสิทธิ์ถอดรหัสคีย์)
  • การป้องกัน Ransomware & Audit: เปิด Versioning + S3 Object Lock (WORM: Write Once, Read Many) ห้ามลบ/แก้ไขภายในเวลาที่กำหนด + ใช้ Amazon Macie ค้นหาข้อมูล PII อัตโนมัติ + CloudTrail เก็บ Log API

1) Plaintext Data + Data Key (DEK) = Ciphertext (เข้ารหัสข้อมูลด้วย DEK ที่เร็วกว่า)
2) Data Key (DEK) + KMS Key (CMK) = Encrypted Data Key (ห่อหุ้ม DEK ด้วย KMS Master Key)
*เก็บ Ciphertext คู่กับ Encrypted DEK ไว้ใน Storage; ส่วน KMS Key อยู่ใน KMS เท่านั้น (หากต้องการ Dedicated HSM มาตรฐาน FIPS 140-2/3 ให้ใช้ CloudHSM)

Deliver (TLS) (ใช้ Client-Side Caching SDK เพื่อลด Latency และประหยัดค่า API $0.05/10,000 calls; คิดค่าเก็บ $0.40/secret/เดือน)

Ransomware & Storage Security 20. เพื่อป้องกันไม่ให้แรนซัมแวร์หรือผู้ไม่หวังดีเข้ามาลบหรือแก้ไขไฟล์สำรองข้อมูลสำคัญในถังเก็บข้อมูล Amazon S3 องค์กรควรเปิดใช้งานฟีเจอร์ Versioning ร่วมกับ __________ (ก) ซึ่งทำงานตามหลักการเขียนครั้งเดียวอ่านได้หลายครั้งหรือ __________ (ข) และใช้บริการ __________ (ค) ในการสแกนค้นหาข้อมูลส่วนบุคคล (PII) ที่อาจหลงเหลืออยู่ในถังเก็บข้อมูลโดยอัตโนมัติ
เฉลย: (ก) S3 Object Lock | (ข) WORM (Write Once, Read Many) | (ค) Amazon Macie

KEV / CVSS Prioritization ข้อที่ 1: ทีมความมั่นคงปลอดภัยตรวจพบช่องโหว่ 2 รายการในระบบขององค์กร ได้แก่ ช่องโหว่ A (CVSS 9.8 แต่อยู่บนเซิร์ฟเวอร์ทดสอบภายในที่ตัดขาดจากอินเทอร์เน็ตและไม่มีข้อมูลสำคัญ) และ ช่องโหว่ B (CVSS 7.2 อยู่บนระบบ API หน้าบ้าน และเพิ่งถูกประกาศอยู่ในบัญชี CISA KEV เมื่อเช้านี้) ทีมควรตัดสินใจดำเนินการอย่างไรตามหลัก Contextual Risk?
  • ก. แก้ไขช่องโหว่ A ก่อนเสมอ เพราะคะแนน CVSS สูงถึงระดับ Critical (9.8)
  • ข. แก้ไขช่องโหว่ B เป็นอันดับแรก เพราะอยู่ในบัญชี CISA KEV ซึ่งมีหลักฐานการถูกโจมตีจริง (Exploit Evidence Accelerator) และอยู่บนระบบที่เปิดรับอินเทอร์เน็ต
  • ค. โอนย้ายความเสี่ยงของช่องโหว่ B ด้วยการซื้อประกันภัยไซเบอร์แทนการอัปเดตแพตช์
  • ง. ปิดระบบทั้งหมดของบริษัททันทีจนกว่าจะอัปเดตแพตช์ครบทั้งสองรายการ
เหตุผล: ตามหลัก Contextual Risk คะแนน CVSS เพียงอย่างเดียวไม่เพียงพอ ต้องดูบริบทธุรกิจ (Exposure, Asset Criticality, Compensating Controls) และช่องโหว่ที่อยู่ใน CISA KEV (Known Exploited Vulnerabilities) ถือเป็น Accelerator (ตัวเร่งความสำคัญสูงสุด) เพราะถูกแฮกเกอร์ใช้โจมตีจริงแล้ว
Evidence Correlation ข้อที่ 2: นักวิเคราะห์ SOC สังเกตเห็นกราฟทราฟฟิกพุ่งสูงขึ้นอย่างผิดปกติ (Traffic Spike) บนแดชบอร์ด Cloudflare Radar มายังเว็บไซต์อีคอมเมิร์ซของบริษัท สิ่งที่นักวิเคราะห์ควรทำเป็นอันดับแรกตามแนวทางปฏิบัติที่ดีที่สุดคือข้อใด?
  • ก. สั่งบล็อก IP ทั้งหมดจากต่างประเทศทันทีและประกาศภาวะวิกฤต (Incident)
  • ข. สั่งรันคำสั่ง terraform destroy เพื่อปิดระบบหนีการโจมตี
  • ค. นำข้อมูลไปตรวจสอบเทียบเคียง (Correlate) กับ Application Logs และสอบถามทีมการตลาดก่อนประกาศ Incident เพราะอาจเกิดจากแคมเปญโปรโมชันของบริษัทเอง
  • ง. บันทึกลงใน Risk Register ว่าข้อมูลรั่วไหลแล้ว (Data Breach) ทันที
เหตุผล: กฎเหล็กในสไลด์ Session 6 Part 1 & 2 คือ "Evidence ไม่ใช่ Risk โดยอัตโนมัติ" และสำหรับ Cloudflare Radar ต้อง Correlate กับ Application Logs เสมอ ก่อนประกาศ Incident เพราะกราฟพุ่งอาจเกิดจากแคมเปญการตลาด ไม่ใช่การโจมตี DDoS เสมอไป
Control Level Impact ข้อที่ 3: ข้อใดอธิบายความแตกต่างของผลกระทบจากการใช้มาตรการควบคุม (Control Effectiveness) ต่อค่าโอกาสเกิด (Likelihood) และค่าผลกระทบ (Impact) ได้ถูกต้องที่สุด?
  • ก. การทำ Backup ข้อมูลแบบ Immutable ช่วยลดค่า Likelihood ของการถูกโจมตีด้วยฟิชชิง
  • ข. การบังคับใช้ MFA และการหมุนเวียนคีย์ (Key Rotation) ช่วยลดค่า Likelihood ส่วนการทำ Network Micro-segmentation และระบบสำรองข้อมูลช่วยลดค่า Impact (จำกัด Blast Radius)
  • ค. การเข้ารหัสข้อมูล (Encryption at Rest) ทำให้คะแนน Inherent Risk ลดลงเป็นศูนย์
  • ง. มาตรการในฟังก์ชัน Protect ของ NIST CSF จะทำงานหลังจากเกิดเหตุการณ์โจมตีสำเร็จแล้วเท่านั้น
เหตุผล: มาตรการป้องกันก่อนเกิดเหตุ เช่น MFA, Key Rotation, Block Public Access จะช่วยลดโอกาสเกิด (ลด Likelihood - L) ส่วนมาตรการกักกันและสำรองข้อมูล เช่น Micro-segmentation และ Backup/Recovery จะช่วยลดความรุนแรงและจำกัดวงความเสียหาย (ลด Impact - I / ลด Blast Radius)
NIST CSF & Incident Response ข้อที่ 4: เมื่อตรวจพบว่า Access Key ของนักพัฒนาหลุดไปอยู่ใน Public GitHub Repository และมีการเรียกใช้งาน API จากต่างประเทศ ข้อใดคือข้อควรระวังที่สำคัญที่สุดในขั้นตอน Respond และ Recover?
  • ก. ลบโพสต์ใน GitHub ทิ้งก็เพียงพอแล้ว ไม่จำเป็นต้องยกเลิกคีย์เดิมเพราะจะทำให้ระบบสะดุด
  • ข. รีบลบ Log และฟอร์แมตเซิร์ฟเวอร์ทั้งหมดทันทีเพื่อไม่ให้แฮกเกอร์ทิ้งร่องรอยไว้
  • ค. ต้องเก็บรักษาหลักฐาน (Preserve Evidence / Logs) ก่อนแก้ไขระบบ, สั่ง Revoke/Rotate คีย์ทันที และต้องตรวจสอบย้อนหลัง (Historical Check) เสมอว่าคีย์นั้นถูกนำไปสร้าง Backdoor หรือดึงข้อมูลใดไปแล้วบ้าง
  • ง. เปลี่ยนจากการใช้ IAM Role กลับไปใช้ Long-lived Access Key เหมือนเดิม
เหตุผล: ในสไลด์ Session 6 Part 2 ระบุชัดเจนว่า ในขั้น Respond ต้อง Preserve evidence เสมอก่อนแก้ไขระบบ และกรณี Credential Leakage การลบคีย์ทิ้งเฉยๆ ไม่เพียงพอ ต้องทำ Historical check (ตรวจประวัติย้อนหลัง) และเช็กว่าไม่มี Backdoor หรือ Policy อันตรายหลงเหลืออยู่ในขั้น Recover
KMS vs Secrets Manager ข้อที่ 5: สถาปนิกซอฟต์แวร์ต้องการออกแบบระบบให้ Microservices จำนวน 80 ตัว เชื่อมต่อกับฐานข้อมูล Amazon RDS โดยห้ามฝังรหัสผ่านไว้ในโค้ด และต้องเปลี่ยนรหัสผ่านฐานข้อมูลอัตโนมัติทุกๆ 30 วันโดยที่ระบบไม่ล่ม (Zero Downtime) ควรเลือกใช้บริการใดและทำงานอย่างไร?
  • ก. ใช้ AWS KMS เพียงอย่างเดียว เพราะ KMS สามารถล็อกอินเข้า RDS ไปเปลี่ยนรหัสผ่านผู้ใช้ได้โดยตรง
  • ข. ใช้ AWS Secrets Manager จัดเก็บรหัสผ่านและตั้งค่า Automated Rotation ผ่าน AWS Lambda โดยมี AWS KMS ทำหน้าที่เข้ารหัสข้อมูลความลับอยู่เบื้องหลัง
  • ค. เก็บรหัสผ่านไว้ในไฟล์ terraform.tfstate แล้วแชร์ไฟล์ไว้บน Public S3 Bucket เพื่อให้ทุกบริการดึงไปใช้ได้ง่าย
  • ง. ใช้ AWS Shield Advanced เพื่อหมุนเวียนรหัสผ่านฐานข้อมูลทุกเดือน
เหตุผล: AWS Secrets Manager ("Fuel Tank") ออกแบบมาเพื่อเก็บ Credentials (รหัสผ่าน DB, API Key) และรองรับ Automated Rotation ผ่าน AWS Lambda โดยไม่เกิด Downtime ส่วน AWS KMS ("Engine") ทำหน้าที่จัดการกุญแจ Cryptographic Key เพื่อเข้ารหัสตัว Secret อีกชั้นหนึ่ง
Secrets Manager Hybrid Use Case ข้อที่ 6: จากกรณีศึกษาการใช้งาน AWS Secrets Manager ทั้ง 5 รูปแบบ หากองค์กรมีแอปพลิเคชันและฐานข้อมูลรันอยู่บนเซิร์ฟเวอร์ภายในองค์กรเอง (On-Premises) แต่ต้องการดึงคีย์ความลับจาก AWS Secrets Manager บนคลาวด์มาใช้งานแบบรวมศูนย์ ต้องใช้กลไกใดควบคู่กัน และมีข้อควรระวังใดที่สำคัญที่สุด?
  • ก. ใช้ S3 Object Lock ร่วมกับ NLB โดยไม่ต้องเชื่อมต่ออินเทอร์เน็ต
  • ข. ใช้ PKI + CA Certificate ผูกกับ IAM Roles Anywhere เพื่อยืนยันตัวตนขอคีย์ และต้องระวังความเสี่ยงเรื่องเครือข่ายอินเทอร์เน็ตหรือสายเคเบิลใต้น้ำขาด จึงควรวางแผนสำรองข้าม Region ไว้ด้วย
  • ค. ส่งคีย์ผ่านทางอีเมลธรรมดาทุกเช้าเพื่อให้แอดมินนำไปใส่ในเครื่อง On-Premises
  • ง. ใช้เฉพาะ AWS WAF ติดตั้งไว้ในห้องเซิร์ฟเวอร์ของบริษัท
เหตุผล: ในเลคเชอร์ Session 7 (Use Case ที่ 4: Enable Hybrid Workload) อธิบายการใช้ PKI + CA Certificate + Trust Policy ร่วมกับ IAM Roles Anywhere เพื่อให้ระบบ On-Premises ดึงคีย์จาก AWS Secrets Manager ได้ และอาจารย์เน้นย้ำข้อควรระวังเรื่องสายอินเทอร์เน็ตใต้น้ำขาด (เช่น สิงคโปร์) ซึ่งต้องมีแผนสำรองข้าม Region
Terraform Steps & State Security ข้อที่ 7: ข้อใดกล่าวถึงขั้นตอนการทำงานของ Terraform (Terraform Workflow) และการจัดการความปลอดภัยของไฟล์ State ได้ถูกต้องตามหลักปฏิบัติสำหรับองค์กร?
  • ก. ลำดับการทำงานคือ Apply → Plan → Init → Destroy และควรอัปโหลดไฟล์ terraform.tfstate ขึ้น GitHub สาธารณะเพื่อให้ทีมงานช่วยกันตรวจทาน
  • ข. ลำดับหลักคือ Init → Plan → Apply → Destroy โดยห้ามนำไฟล์ terraform.tfstate ขึ้น Git เด็ดขาดเพราะเก็บข้อมูลความลับเป็น Plaintext แต่ต้องเก็บใน Remote Backend (เช่น S3 ที่เข้ารหัสด้วย KMS และทำ State Locking ด้วย DynamoDB)
  • ค. คำสั่ง terraform plan จะทำการลบฐานข้อมูลจริงบนคลาวด์ทันทีโดยไม่ถามยืนยัน
  • ง. Terraform เป็นเครื่องมือแบบ Imperative ที่ไม่สามารถตรวจจับ Configuration Drift ได้
เหตุผล: วงจร 4 ขั้นตอนหลักของ Terraform คือ Init → Plan → Apply → Destroy และไฟล์ terraform.tfstate มีข้อมูลโครงสร้างและ Secrets แบบ Plaintext จึงห้าม Commit ลง Git เด็ดขาด ต้องเก็บใน Remote State ที่มีการเข้ารหัสและจำกัดสิทธิ์

Zero Trust Architecture ข้อที่ 10: ข้อใดเปรียบเทียบแนวคิดของสถาปัตยกรรม Zero Trust กับระบบความปลอดภัยแบบดั้งเดิม (Castle-and-Moat) และขั้นตอนการนำไปใช้งานได้ถูกต้องที่สุด?

  • ข. ขั้นตอนแรกของ Zero Trust คือการซื้อฮาร์ดแวร์ไฟร์วอลล์ตัวใหญ่ที่สุดมาวางไว้ที่หน้าทางออกอินเทอร์เน็ตเพียงจุดเดียว
  • ค. Zero Trust ยึดหลัก "Never Trust, Always Verify" โดยเริ่มจากกำหนด Protection Surface (DAAS) แล้วสำรวจ Data Flows จากนั้นทำ Micro-segmentation เพื่อป้องกัน Lateral Movement และสร้างนโยบายด้วย Kipling Method (Who, What, When, Where, Why, How)
  • ง. ระบบเก่า (Legacy Systems) ไม่สามารถนำมาเชื่อมต่อในสภาพแวดล้อม Zero Trust ได้เลย ต้องทุบทิ้งสถานเดียว
เหตุผล: Zero Trust ยกเลิกการเชื่อใจโดยปริยาย (Implicit Trust) ของ Castle-and-Moat เปลี่ยนเป็น "Never Trust, Always Verify" ตามขั้นตอน 5-Step Blueprint: 1. Define Protection Surface (DAAS) → 2. Map Data Flows → 3. Design ZTA (Micro-segmentation กัน Lateral Movement) → 4. Create Policies (MFA/Least Privilege) → 5. Monitor & Kipling Method (ส่วนระบบ Legacy สามารถใช้ Reverse Proxy / API Gateway กั้นหน้าได้)

Envelope Encryption (KMS) ข้อที่ 12: เหตุใดระบบคลาวด์จึงเลือกใช้กระบวนการ Envelope Encryption แทนการนำ KMS Master Key (CMK) ไปเข้ารหัสไฟล์ข้อมูลขนาดหลายเทราไบต์โดยตรง และการจัดเก็บคีย์ที่ถูกต้องเป็นอย่างไร?
  • ก. เพราะ KMS Master Key สามารถส่งออกไปเก็บไว้ในเครื่องโน้ตบุ๊กของพนักงานทุกคนได้อย่างอิสระ
  • ข. เพื่อประสิทธิภาพความเร็วและความปลอดภัยสูงสุด โดยระบบจะใช้ Data Key (DEK) เข้ารหัสไฟล์ข้อมูลให้เป็น Ciphertext แล้วใช้ KMS Key เข้ารหัสห่อหุ้ม Data Key อีกชั้น ทั้งนี้จะเก็บ Ciphertext คู่กับ Encrypted Data Key ไว้ใน Storage ส่วน KMS Key จะถูกเก็บรักษาไว้ใน KMS เท่านั้นและไม่เคยออกจาก KMS
  • ค. เพราะการเข้ารหัสด้วย Data Key ไม่จำเป็นต้องมีการถอดรหัสเมื่อนำข้อมูลกลับมาใช้
  • ง. เพื่อลดความทนทานของ S3 จาก 11 Nines ให้เหลือ 3 Nines
เหตุผล: หลักการ Envelope Encryption ในสไลด์ Session 7 คือ 1) Plaintext Data + Data Key = Ciphertext และ 2) Data Key + KMS Key = Encrypted Data Key โดยเก็บ Ciphertext คู่กับ Encrypted Data Key ไว้ใน Storage ส่วนตัว KMS Key (Master Key) จะอยู่ในตู้เซฟ KMS ตลอดเวลา ไม่เคยถูกส่งออกนอก KMS

  • ข. เสาหลัก Reliability เน้นการขยายระบบแนวราบ (Scale horizontally to increase aggregate system availability) และจัดการการเปลี่ยนแปลงด้วยระบบอัตโนมัติ (Manage change in automation) ส่วนเสาหลัก Operational Excellence เน้นทำการเปลี่ยนแปลงขนาดเล็ก บ่อยครั้ง และย้อนกลับได้ (Make frequent, small, reversible changes)
