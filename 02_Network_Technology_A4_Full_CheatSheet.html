5.1 Transport Service & Mux/Demux
  • Transport = สื่อสาร process-to-process (Network = host-to-host) ทำงานที่ end system เท่านั้น router ไม่ดู L4
  • Port 16 bit: 0–1023 well-known, 1024–49151 registered, 49152–65535 ephemeral
  • UDP demux ด้วย (dstIP, dstPort) → ต่างต้นทางเข้า socket เดียวกัน
  • TCP demux ด้วย 4-tuple (srcIP, srcPort, dstIP, dstPort) → 1 connection = 1 socket (web server มีหลาย socket port 80)
5.2 UDP (RFC 768)
Header 8 bytes: SrcPort | DstPort | Length | Checksum
Checksum = ผลรวม 16-bit แบบ 1's complement แล้วกลับบิต (ตรวจผิดพลาดได้ แต่ไม่แก้/ไม่ส่งซ้ำ)
ข้อดี: ไม่ต้อง handshake (ไม่มี delay ตั้ง conn), ไม่มี state, header เล็ก, ไม่มี congestion control → แอปคุมอัตราเอง
ใช้กับ: DNS, SNMP, DHCP, VoIP, streaming สด, เกม, QUIC/HTTP3, CoAP • ถ้าต้องการ reliable ให้ทำที่ชั้นแอป

5.5 Connection Management
3-Way Handshake: ① SYN(seq=x) → ② SYN+ACK(seq=y, ack=x+1) → ③ ACK(ack=y+1) [③ ส่ง data ได้]
ทำไม 3 ไม่ใช่ 2: ยืนยันว่าทั้งสองฝั่งรับ-ส่งได้ + sync ISN สองทาง + กัน SYN เก่าที่ค้างในเครือข่าย
ปิด (4-way): FIN → ACK → FIN → ACK → ฝั่งที่ปิดก่อนรอ TIME_WAIT = 2MSL (เผื่อ ACK สุดท้ายหาย)
States: CLOSED→LISTEN→SYN_RCVD→ESTABLISHED / SYN_SENT • FIN_WAIT_1→FIN_WAIT_2→TIME_WAIT • CLOSE_WAIT→LAST_ACK
SYN Flood = ส่ง SYN ปลอมจน half-open เต็ม → แก้ด้วย SYN cookies • RST = ยกเลิก conn ทันที
5.6 RTT & RTO — ข้อสอบ Q1 ★★★
EstimatedRTT = (1−α)·EstRTT + α·SampleRTT α=0.125 DevRTT = (1−β)·DevRTT + β·|SampleRTT − EstRTT| β=0.25 TimeoutInterval (RTO) = EstimatedRTT + 4·DevRTT EWMA: ค่าใหม่มีน้ำหนักมากกว่า ค่าเก่าหายแบบ exponential • DevRTT = margin ที่ขยาย/หดตามความแกว่ง
RTO ต่ำไป (เช่น 3 ms เมื่อ RTT 3–7 ms) → Premature timeout ส่งซ้ำทั้งที่ยังไม่หาย → เปลือง BW, ข้อมูลซ้ำ, TCP คิดว่า congest ลด cwnd ผิด ๆ
RTO สูงไป → แพ็กเก็ตหายจริงต้องรอนาน (slow loss recovery) throughput ต่ำ
RTO = 8 ms กับ RTT 3–7 ms → ครอบคลุม ไม่ timeout เกิน ✓ (แต่ถ้าสูงมากเกินไปก็กู้ช้า)
ตั้ง RTO ที่ดี: ต้องพิจารณา ค่าเฉลี่ย + ความแปรปรวน (variance) ของ RTT, ปรับแบบ adaptive ไม่ใช่ค่าคงที่ • สูตรเก่า RTO = 2×EstRTT ไม่สนความแกว่ง ✗
Karn's Algorithm: ไม่วัด SampleRTT จาก segment ที่ส่งซ้ำ (ไม่รู้ว่า ACK ตอบตัวไหน) + เมื่อ timeout → RTO × 2 (exponential backoff)
ตัวอย่าง: Est=5, Dev=1, Sample=7 → Est=0.875·5+0.125·7=5.25 • Dev=0.75·1+0.25·|7−5.25|=1.1875 • RTO=5.25+4.75=10.0 ms (ถ้าใช้ Est เดิมหา diff: Dev=1.25 → RTO=10.25 — เขียนสูตรกำกับ)
5.7 TCP Reliability Mechanisms
  • Cumulative ACK + timer เดียว (segment เก่าสุดที่ยังไม่ ACK)
  • Timeout → ส่งซ้ำ segment นั้น + RTO×2
  • Fast Retransmit: ได้ 3 duplicate ACK → ส่งซ้ำทันทีไม่รอ timeout
  • Delayed ACK: รอ ≤ 500 ms (มัก 200) เพื่อ ACK ทีเดียว 2 segment
  • out-of-order → ส่ง dup ACK ทันที, ช่องว่างถูกเติม → ACK ทันที
5.8 Flow Control & Advertised Window — Q3
Advertised Window (rwnd) = ผู้รับบอกพื้นที่ว่างใน receive buffer ผ่าน header ทุก segment → ผู้ส่งต้องไม่ส่งเกิน = กันผู้รับล้น
rwnd = RcvBuffer − (LastByteRcvd − LastByteRead) LastByteSent − LastByteAcked ≤ rwnd EffectiveWindow = min(rwnd, cwnd) − (LastByteSent − LastByteAcked) rwnd = 0 → ผู้ส่งส่ง zero-window probe 1 byte (persist timer) จนกว่า rwnd > 0
Silly Window Syndrome → แก้ด้วย Nagle (ผู้ส่งรวมข้อมูลเล็ก) / Clark (ผู้รับไม่ประกาศ window เล็ก)
5.9 Congestion Control — Slow Start / AIMD
สาเหตุ/ผล: คิวยาว → delay ↑, packet loss → ส่งซ้ำเปลือง, upstream ส่งเปล่าเมื่อทิ้งปลายทาง
แนวทาง: End-to-end (TCP เดาจาก loss/delay) vs Network-assisted (DECbit, ECN)
cwnd = ผู้ส่งประเมินเอง (กันเครือข่ายล้น) ↔ rwnd (กันผู้รับล้น) • rate ≈ cwnd/RTT
Slow Start: เริ่ม cwnd = 1 MSS, ทุก ACK +1 MSS → ×2 ทุก RTT (exponential) จนถึง ssthresh/เกิด loss (ชื่อ slow เพราะเริ่มจาก 1 แต่โตเร็วมาก)
Congestion Avoidance: cwnd ≥ ssthresh → +1 MSS ต่อ RTT (linear)
AIMD: Additive Increase +1 / Multiplicative Decrease ÷2 → กราฟฟันเลื่อย (sawtooth), แบ่ง BW อย่าง fair

5.10 DECbit (Congestion Avoidance แบบ router ช่วย)
Router ตั้ง congestion bit ในแพ็กเก็ตเมื่อ avg queue length ≥ 1 → ผู้รับคัดลอกใส่ ACK
ผู้ส่งดูแพ็กเก็ตใน window ล่าสุด: < 50% bit set → cwnd + 1 • ≥ 50% → cwnd × 0.875
ตัวอย่าง: 6/10 set, cwnd 16 → 16×0.875 = 14 • ต่อยอดเป็น ECN: router mark CE ใน IP header → ผู้รับตั้ง ECE ใน TCP ACK → ผู้ส่งลด cwnd + ตั้ง CWR
5.11 RED — Random Early Detection — Q2 ★★★
AvgLen = (1−Weight)·AvgLen + Weight·SampleLen AvgLen < MinTh → Pdrop = 0 (ผ่าน 100%) MinTh ≤ AvgLen < MaxTh → Pdrop = Pmax·(AvgLen−MinTh)/(MaxTh−MinTh) AvgLen ≥ MaxTh → Pdrop = 1 (ทิ้ง 100%) PThroughput = (1 − Pdrop) × 100% #ผ่าน = N·(1−Pdrop) Sample: MinTh=10, MaxTh=15, RED-1 Pmax=0.5, RED-2 Pmax=0.7
Avg=10 → P=0 → 100% ทั้งคู่ • Avg=18 → P=1 → 0% ทั้งคู่
Avg=13 → RED-1: 0.5×3/5=0.30 → 70% • RED-2: 0.7×3/5=0.42 → 58%
เก็ง: Avg=12 RED-2 → P=0.28 (ผ่าน 72%) • Avg=14, 500 pkt, RED-1 → P=0.4 ทิ้ง 200 ผ่าน 300 • ต้องการผ่าน 80% บน RED-1 → 0.2=0.5(x−10)/5 → x=12
ทำไมใช้ AvgLen (time-averaged)? กรอง burst ชั่วคราว (รถทัวร์เข้าเซเว่น แป๊บเดียวก็ว่าง) ไม่ทิ้งเกินเหตุ แต่ตอบสนอง congestion ระยะยาว
ทำไมสุ่มทิ้งก่อนเต็ม? เตือน TCP แต่เนิ่น ๆ (implicit) + ป้องกัน Global Synchronization (Drop-tail ทิ้งทีเดียวทุก flow → ลด cwnd พร้อมกัน → link ว่างสลับแน่น) + flow ที่ส่งมากโดนทิ้งมาก (fair)
Pmax สูง (RED-2) = aggressive: คิวสั้น delay ต่ำ แต่ throughput ลด • Pmax ต่ำ = throughput สูง แต่คิวยาว
กับดัก: โจทย์ถาม drop หรือ throughput? • Avg = MinTh → P=0 • Avg ≥ MaxTh → P=1 ไม่ใช่ Pmax

6.3 HTTP & Web
HTTP = stateless, request/response บน TCP • methods: GET, POST, HEAD, PUT, DELETE
Status: 200 OK • 301 Moved • 304 Not Modified • 400 Bad Request • 404 Not Found • 500/505
Non-persistent (1.0): 2·RTT + ttrans ต่อ object (เปิด TCP ใหม่ทุกครั้ง) • Persistent (1.1): conn เดียว ~1 RTT/object, pipelining แต่ HOL blocking
HTTP/2: binary framing, multiplex stream ใน TCP เดียว, header compression (HPACK), server push, priority — แต่ยังมี HOL ที่ระดับ TCP
HTTP/3: บน QUIC/UDP แก้ HOL ระดับ transport
Cookie 4 ส่วน: Set-Cookie ใน response, Cookie ใน request, ไฟล์ใน browser, DB ฝั่ง server → เก็บ state บน HTTP

7.3 CSMA/CA, SIFS vs DIFS — Q7 ★★
ผู้ส่ง: ① ช่องว่างนาน DIFS → ส่งทั้งเฟรม (ไม่ตรวจชนระหว่างส่ง) ② ช่องไม่ว่าง → สุ่ม backoff, นับถอยหลังเมื่อช่องว่าง, หยุดนับ (freeze) เมื่อไม่ว่าง → ถึง 0 ส่ง ③ ไม่ได้ ACK → เพิ่มช่วงสุ่ม (×2) ทำใหม่
ผู้รับ: เฟรมถูกต้อง → รอ SIFS → ส่ง ACK
ลำดับ: SIFS < PIFS < DIFS (สั้น = priority สูง) • PIFS = AP ใช้ใน PCF
ทำไม ACK รอ SIFS ไม่ใช่ DIFS? SIFS สั้นกว่า → ACK (และ CTS) ได้สิทธิ์ใช้ช่องก่อน สถานีอื่นที่ต้องรอ DIFS → สถานีอื่นเห็นช่องไม่ว่าง ไม่มีใครแทรก → ACK ไม่ชน
ถ้ารอ DIFS: สถานีอื่นที่รอ DIFS เหมือนกันอาจส่ง DATA พร้อม ACK → ชน → ผู้ส่งไม่ได้ ACK → timeout ส่ง DATA ทั้งเฟรมซ้ำ เปลือง airtime
7.4 Hidden vs Exposed Terminal + RTS/CTS — Q6 ★★★
Hidden Terminal: A และ C อยู่ในระยะ B แต่ ไม่ได้ยินกันเอง (ไกล/สิ่งกีดขวาง/fading) → carrier sense ว่าว่าง → ส่งพร้อมกัน → ชนที่ B
A )))) B (((( C A ✗ ได้ยิน C แก้ด้วย RTS/CTS: A ส่ง RTS (สั้น, มี duration) → B ตอบ CTS ที่ทุกคนรอบ B ได้ยิน (รวม C) → C ตั้ง NAV งดส่งตาม duration → A ส่ง DATA → B ACK • ถ้าชนก็ชนแค่ RTS สั้น ๆ ไม่เสียมาก • ใช้เมื่อเฟรมยาวเกิน RTS threshold
NAV (Network Allocation Vector) = virtual carrier sensing จากฟิลด์ Duration
Exposed Terminal: S1 → R1 กำลังส่ง; S2 อยู่ในระยะ S1 จึงงดส่งไป R2 ทั้งที่ R2 อยู่นอกระยะ S1 (ส่งได้ไม่รบกวน) → เสียโอกาส
R1 ← S1 )))) S2 → R2 S2 ✗ ไม่กล้าส่ง RTS/CTS ช่วย: S2 ได้ยิน RTS ของ S1 แต่ ไม่ได้ยิน CTS ของ R1 → รู้ว่าไม่ได้อยู่ใกล้ผู้รับ → ส่งได้
สรุป: Hidden = ชนเพราะไม่รู้ • Exposed = เงียบโดยไม่จำเป็น

7.7 Mobility & Mobile IP — Q9 ★★
Home network / Home Agent (HA) ≈ ตม.ไทย • Visited network / Foreign Agent (FA) ≈ ตม.ลาว • Permanent address = IP ถาวร (คนอื่นใช้ติดต่อ) • COA (Care-of-Address) = ที่อยู่ชั่วคราวใน visited net
ขั้นพื้นฐาน: Agent discovery (ICMP agent advertisement) → Registration (FA → HA) → Indirect routing (tunnel)
Indirect Routing 6 ขั้น:
① Mobile เข้า visited net → ลงทะเบียนกับ FA ได้ COA
② FA แจ้ง COA ให้ HA (registration)
③ Correspondent ส่งไป permanent address → ถึง home net
④ HA ดักรับ → encapsulate (IP-in-IP tunnel) → COA
⑤ FA decapsulate → ส่งต่อให้ mobile
⑥ Mobile ตอบตรงไป correspondent (src = permanent)
ปัญหา: Triangle Routing อ้อมผ่าน HA แม้ correspondent อยู่ใกล้ mobile • ข้อดี: โปร่งใสต่อ correspondent, conn ไม่หลุดเมื่อย้าย
Direct Routing: correspondent agent ถาม HA ขอ COA → tunnel ตรงไป FA → เส้นทางสั้น แต่ไม่โปร่งใส + ถ้าย้ายต่อต้องใช้ anchor FA ส่งต่อไป FA ใหม่

9.3 Q10 — งานวิจัยที่เพื่อนพรีเซนต์ (Concept)
① ECH (Encrypted Client Hello): ปัญหา = SNI ใน TLS ClientHello เป็น plaintext → ISP/คนกลางรู้ว่าเข้าเว็บไหนแม้ใช้ HTTPS • ECH แบ่ง Outer ClientHello (SNI สาธารณะของ CDN เช่น Cloudflare) + Inner ClientHello เข้ารหัส (SNI จริง) ด้วย public key จาก DNS HTTPS record (ควรใช้คู่ DoH) • GREASE = client ส่ง ECH ปลอมแบบสุ่มเสมอ → middlebox แยกไม่ออก ไม่ ossify/บล็อก extension ใหม่ • ผลกระทบ: firewall/content filter กรองด้วย SNI ไม่ได้
② Edge Jamming Detection ด้วย 1D-CNN: jammer ส่งสัญญาณรบกวนกลบช่อง • ใช้ค่า RSS เป็นอนุกรมเวลา → 1D-CNN จำแนก Normal / Constant / Periodic • Constant jammer (AWGN ต่อเนื่อง RSS สูงตลอด) แม่น 100% • Periodic (สลับส่ง/เงียบ ช่วงเงียบเหมือน normal) ~72% • รวม 86.3% บน Raspberry Pi + HackRF SDR • ทำไม Edge? ถูก jam แล้วส่งข้อมูลไป cloud ไม่ได้ ต้องตัดสินใจที่อุปกรณ์เอง + latency ต่ำ
③ IoT DDoS Detection ด้วย ML: IoT ใช้ default password, ไม่ค่อย patch, ทรัพยากรน้อย → มัลแวร์ Mirai/Bashlite สแกน (Telnet) ยึดเครื่องเป็น botnet → C&C สั่งยิง DDoS: Volumetric (UDP flood), Protocol (SYN flood), Application (HTTP flood) • Signature-based ✗: จับได้แค่ที่รู้จัก, traffic IoT หลากหลาย/เปลี่ยนเร็ว, ติดตั้งบนอุปกรณ์เล็กไม่ได้ → ML ที่ gateway (Random Forest, XGBoost, SVM, KNN) เรียนรู้ feature traffic (pkt rate, size, flag) จับ anomaly รวมถึงการโจมตีใหม่
