1. ที่มาที่ไป: ทำไมระบบเครือข่ายต้องแบ่งเป็นลำดับชั้น (Layered Architecture)?

ที่มาที่ไปและเหตุผลเชิงวิศวกรรม (Why It Exists & First Principles)

ในยุคเริ่มต้นของคอมพิวเตอร์ (ทศวรรษ 1960–1970) บริษัทผู้ผลิตแต่ละราย (เช่น IBM, DEC) สร้างระบบเครือข่ายแบบผูกขาดเฉพาะยี่ห้อ (Proprietary Monolithic Systems) ที่รวมตั้งแต่สายไฟ การแปลงสัญญาณไฟฟ้า การหาเส้นทาง ไปจนถึงตัวโปรแกรมแสดงผลไว้ด้วยกัน ทำให้คอมพิวเตอร์คนละยี่ห้อคุยกันไม่ได้เลย และหากต้องการเปลี่ยนสายสัญญาณจากสายทองแดงเป็นสายไฟเบอร์ออปติก ก็ต้องรื้อเขียนโปรแกรมใหม่ทั้งหมด!

2. ทฤษฎีชั้นกายภาพ (Physical Layer): ความสูญเสียของสัญญาณและประเภทของสัญญาณรบกวน (Noise)

ในการส่งสัญญาณจากต้นทางไปยังปลายทางผ่านสื่อกลาง (สายทองแดง UTP, สายใยแก้วนำแสง Fiber Optic หรือคลื่นวิทยุไร้สาย) สัญญาณจะถูกลดทอนคุณภาพจากปัจจัยทางฟิสิกส์ 3 ประการ:

  1. Attenuation (การลดทอนความแรงของสัญญาณ): พลังงานของคลื่นลดลงตามระยะทางที่เพิ่มขึ้น จึงต้องมีตัวทวนสัญญาณ (Repeater / Amplifier)
  2. Delay Distortion (ความเพี้ยนเนื่องจากความเร็วเฟสต่างกัน): ความถี่องค์ประกอบต่างๆ ของสัญญาณเดินทางในสายด้วยความเร็วไม่เท่ากัน ทำให้รูปคลื่นบิดเบี้ยวเมื่อถึงปลายทาง
  3. Noise (สัญญาณรบกวน — จุดเน้นสำคัญจากเลคเชอร์!): เป็นสาเหตุหลักที่ทำให้จุดสัญญาณคลาดเคลื่อนไปจากตำแหน่งที่ควรจะเป็นในแผนภาพกลุ่มดาว (Constellation Diagram) จนผู้รับแปลค่าบิตผิดเพี้ยนจาก 0 เป็น 1 หรือจาก 1 เป็น 0 (Bit Error) โดยอาจารย์ได้จำแนก Noise ออกเป็น 2 ประเภทหลัก:
ประเภทของสัญญาณรบกวนสาเหตุการเกิดในธรรมชาติลักษณะความเสียหายต่อข้อมูล (Error Pattern)
1. White Noise (Thermal Noise)เกิดจากการเคลื่อนที่ด้วยความร้อนของอิเล็กตรอนในตัวนำไฟฟ้า เกิดขึ้นตลอดเวลาอย่างสม่ำเสมอในทุกความถี่มักทำให้เกิดความผิดพลาดแบบบิตเดี่ยว (Single-bit Error คือผิดเพี้ยนเพียง 1–2 บิตกระจัดกระจาย)
2. Impulse Noise (Color Noise)เกิดขึ้นเป็นจังหวะกระโชกช่วงสั้นๆ แต่รุนแรง เช่น สัญญาณรบกวนจากเตาไมโครเวฟ มอเตอร์ไฟฟ้า หรือฟ้าผ่าทำให้เกิด Burst Error (ข้อมูลผิดพลาดติดต่อกันเป็นชุดยาวหลายบิต) ซึ่ง ยิ่งระบบมีความเร็วการส่งข้อมูล (Data Rate) สูงเท่าใด ช่วงเวลา 1 วินาทีที่เกิด Impulse Noise ก็จะยิ่งทำลายจำนวนบิตเสียหายมากขึ้นเท่านั้น!

3. ปัญหา Clock Skew และกลไกการเข้ารหัสสัญญาณ 4B/5B ร่วมกับ NRZI (เนื้อหาเน้นย้ำจากเลคเชอร์!)

ประเด็นเน้นย้ำในห้องเรียนโดยอาจารย์ผู้สอน (Classroom Lecture Insight)

ในการบรรยายสัปดาห์ที่ 1 ได้อธิบายที่มาที่ไปของ Line Coding แบบ 4B/5B ร่วมกับ NRZI อย่างละเอียด:

• ต้นตอของปัญหา (Clock Skew Problem): ในการส่งข้อมูลดิจิทัล ฝั่งผู้ส่งและฝั่งผู้รับมีนาฬิกา (Clock) คนละเรือน หากเราส่งสัญญาณแบบตรงไปตรงมา (เช่น บิต 0 แทนด้วยแรงดัน 0V และบิต 1 แทนด้วย +5V) แล้วบังเอิญข้อมูลที่จะส่งมีเลข 0 ติดต่อกันยาว 100 ตัว (0000000...) สัญญาณบนสายจะเป็นเส้นตรงนิ่งสนิท! เมื่อไม่มีการเปลี่ยนแปลงระดับแรงดัน (No Signal Transition) นาฬิกาของฝั่งผู้รับจะเริ่มเดินคลาดเคลื่อน (Clock Skew / Loss of Synchronization) จนไม่รู้ว่ามีเลข 0 ผ่านไปกี่ตัวแล้ว (เช่น ส่งมา 100 ตัว แต่อาจอ่านได้ 98 หรือ 102 ตัว)

• ทำไม NRZI อย่างเดียวแก้ได้แค่ครึ่งเดียว? การเข้ารหัสแบบ NRZI (Non-Return-to-Zero Inverted) มีกฎว่า: "ถ้าเจอบิต 1 ให้สลับระดับสัญญาณ (Transition) แต่ถ้าเจอบิต 0 ให้คงระดับสัญญาณเดิมไว้ (No Transition)" ดังนั้น NRZI จึงแก้ปัญหาบิต 1 ติดกันยาวๆ ได้แล้ว (เพราะสลับขึ้นลงตลอด) แต่ถ้าเจอบิต 0 ติดกันยาวๆ สัญญาณก็ยังนิ่งเป็นเส้นตรงเหมือนเดิม!

ทางออกอัจฉริยะ: การแปลงรหัส 4B/5B ก่อนส่งให้ NRZI

เพื่อกำจัดไม่ให้มีเลข 0 ติดกันยาวๆ ก่อนส่งเข้า NRZI วิศวกรจึงคิดค้นตารางแปลงรหัส 4B/5B (4-Bit to 5-Bit Encoding):

  1. หลักการทำงาน: นำข้อมูลต้นฉบับทีละ 4 บิต (ซึ่งมีรูปแบบที่เป็นไปได้ทั้งหมด $2^4 = 16$ รูปแบบ ตั้งแต่ 0000 ถึง 1111) ไปเปิดตารางแปลงเป็นรหัสใหม่ขนาด 5 บิต (ซึ่งมีทั้งหมด $2^5 = 32$ รูปแบบ)
  2. กฎการคัดเลือกรหัส 5 บิต: คัดเลือกเฉพาะรหัส 5 บิตที่ มีเลข 0 นำหน้าไม่เกิน 1 ตัว และมีเลข 0 ปิดท้ายไม่เกิน 2 ตัว ดังนั้นเมื่อนำรหัส 5 บิตมาวางต่อกัน จะรับประกันได้ 100% ว่า จะไม่มีทางเกิดเลข 0 ติดต่อกันเกิน 3 ตัวในสายสัญญาณ (ในเลคเชอร์สรุปว่าป้องกันไม่ให้มีเลข 0 ติดกันเกิน 2–3 ตัว) ทำให้เมื่อส่งต่อเข้าวงจร NRZI จะเกิดการเปลี่ยนสถานะของสัญญาณ (Transition) อย่างสม่ำเสมอตลอดเวลา ปลายทางจึงซิงค์สัญญาณนาฬิกา (Clock Recovery) ได้อย่างแม่นยำ!
  3. การคำนวณประสิทธิภาพ (Efficiency):
สมการและการคำนวณ (Mathematical Formulation & Step-by-Step Calculation)
สูตรการคำนวณประสิทธิภาพของรหัส 4B/5B:
  เนื่องจากทุกๆ 5 บิตที่ถูกส่งออกไปบนสายสัญญาณ จะบรรจุข้อมูลจริง (Useful Data) อยู่ 4 บิต (และเป็น Overhead 1 บิต)
  ดังนั้น:
    Efficiency = (จำนวนบิตข้อมูลจริง / จำนวนบิตที่ส่งจริง) × 100%
               = (4 / 5) × 100% = 80%
  (หมายเหตุ: รหัส 5 บิตที่เหลืออีก 32 - 16 = 16 รูปแบบ จะถูกนำไปใช้เป็นรหัสควบคุม Control Symbols เช่น Start/End of Frame หรือ Idle และรหัสที่ห้ามใช้เพื่อตรวจจับ Error)

4. กรณีศึกษางานวิจัย: การตรวจจับและจำแนกสัญญาณรบกวน (Jamming) บนอุปกรณ์ Edge ด้วยโมเดล 1D-CNN

ในชั้นเรียนมีการอภิปรายงานวิจัยสมัยใหม่เรื่องการรักษาความมั่นคงปลอดภัยในระดับ Physical/Wireless Layer ต่อการโจมตีด้วยการปล่อยคลื่นรบกวน (Jamming Attack) ซึ่งมีประเด็นสำคัญดังนี้:

  1. ประเภทของสัญญาณรบกวน (Jammer Types):
  • Constant Jammer (รบกวนต่อเนื่อง): ปล่อยคลื่นพลังงานรบกวนออกมาตลอดเวลา ทำให้ค่าความแรงสัญญาณรับ (RSS — Received Signal Strength) สูงค้างผิดปกติตลอดเวลา จึง ตรวจจับได้ง่ายที่สุด
  • Periodic Jammer (รบกวนเป็นจังหวะสลับช่วงพัก): ปล่อยสัญญาณรบกวนสลับกับหยุดพักเป็นคาบเวลา ทำให้ในช่วงที่หยุดพัก ค่า RSS จะดูคล้ายกับสัญญาณปกติมาก จึงเป็น โจทย์ที่ท้าทายที่สุดในการจำแนก
  1. ช่องว่างของงานวิจัยเดิม (Research Gaps): งานวิจัยในอดีตมักใช้เพียงข้อมูลจำลองในคอมพิวเตอร์ (Simulation) ไม่ได้ทดสอบกับฮาร์ดแวร์จริง, บอกได้แค่ว่าถูกรบกวนหรือไม่แต่แยกประเภท Jammer ไม่ได้ และยังไม่เคยนำไปรันบนอุปกรณ์พกพาขนาดเล็ก (Edge Device) แบบเรียลไทม์
  2. สถาปัตยกรรมการทดลองและโมเดล 1D-CNN:
  • ฮาร์ดแวร์จริง: ใช้อุปกรณ์รับสัญญาณวิทยุ HackRF SDR ที่ความถี่ Wi-Fi ช่องที่ 1 (2.412 GHz) ต่อเข้ากับบอร์ดประมวลผลขนาดเล็ก Raspberry Pi 3
  • ชุดข้อมูลจริง (Open-source Dataset): เก็บข้อมูลสัญญาณจริงจำนวน 1,230 ชุด แบ่งเป็น 3 สถานะ คือ Normal (ปกติ), Constant Jammer และ Periodic Jammer
  • ทำไมต้องใช้ 1D-CNN (1-Dimensional Convolutional Neural Network)? เพราะข้อมูลค่าความแรงสัญญาณ RSS ตามเวลาเป็นข้อมูลอนุกรมเวลา 1 มิติ (Time-Series Data) โมเดล 1D-CNN จึงสกัดคุณลักษณะเด่น (Feature Extraction) ได้ตรงจุด มีขนาดไฟล์โมเดลเล็ก ประมวลผลเร็ว และกินทรัพยากรบน Raspberry Pi ต่ำมาก
  1. ผลการทดลองและแนวทางพัฒนาต่อ:
  • ความแม่นยำรวมบนอุปกรณ์ Edge แบบ Real-time อยู่ที่ 86.3%
  • จำแนก Constant Jammer ได้แม่นยำ 100%
  • จำแนก Periodic Jammer ได้ 72% (เนื่องจากช่วงพักมีความคล้ายคลึงกับสัญญาณปกติมาก จึงควรพัฒนาต่อด้วยการใช้เทคนิค Signal Processing / Denoising ช่วยกรองสัญญาณ, เพิ่มความหลากหลายของข้อมูลเพื่อแก้ปัญหา Overfitting และทดสอบกับอุปกรณ์เคลื่อนที่จริง เช่น โดรน หรือ Internet of Vehicles)
บทที่ 2 (Weeks 1–2)

ชั้นเชื่อมโยงข้อมูล (Data Link Layer), การตรวจจับ/กู้คืนข้อผิดพลาด (CRC & ARQ) และโปรโตคอล MAC

Parity Check, การหารยาว CRC Polynomial, กลไก ARQ (Stop-and-Wait, Go-Back-N, Selective Repeat), CSMA/CD และที่มาของ Slot Size 512 bits

1. บทบาทหน้าที่ของชั้นเชื่อมโยงข้อมูล (Data Link Layer - Layer 2)

หากชั้น Network Layer (Layer 3) มีหน้าที่วางแผนการเดินทางข้ามโลกจากกรุงเทพฯ ไปนิวยอร์ก ชั้น Data Link Layer (Layer 2) ก็คือผู้ที่รับผิดชอบการขนส่งเฟรมข้อมูล ระหว่างอุปกรณ์สองตัวที่เชื่อมติดกันในลิงก์เดียว (Node-to-Node / Hop-to-Hop Delivery) โดยแบ่งออกเป็น 2 ชั้นย่อย (Sublayers):

  1. LLC (Logical Link Control): ดูแลเรื่องการควบคุมการไหลของข้อมูล (Flow Control) และการตรวจจับ/กู้คืนข้อผิดพลาด (Error Detection & Recovery)
  2. MAC (Media Access Control): ดูแลเรื่องที่อยู่ทางกายภาพ (MAC Address 48-bit Hexadecimal เช่น 00:1A:2B:3C:4D:5E) และการบริหารจัดการสิทธิ์ว่าใครจะได้ส่งข้อมูลลงบนสื่อกลางที่ใช้ร่วมกัน (Shared Broadcast Medium) เพื่อป้องกันข้อมูลชนกัน

2. กลไกการตรวจจับข้อผิดพลาด (Error Detection): Parity Check vs CRC

เมื่อคลื่นสัญญาณถูกรบกวนด้วย Noise ในชั้น Physical Layer จนบิตเพี้ยน ฝั่งผู้รับจะรู้ได้อย่างไรว่าข้อมูลที่ได้รับมานั้นถูกต้องหรือเสียหาย? หลักการพื้นฐานคือฝั่งผู้ส่งต้องคำนวณและเติม บิตตรวจสอบส่วนเกิน (Redundant Bits / Error-Detecting Code) ต่อท้ายข้อมูลไปให้ฝั่งผู้รับตรวจสอบ:

2.1 Parity Check (การตรวจสอบภาวะคู่-คี่)

  • หลักการ: เติมบิตพิเศษเข้าไปเพียง 1 บิต (Parity Bit) ต่อท้ายข้อมูล:
  • Even Parity (พาริตีคู่): เติม 0 หรือ 1 เพื่อให้ผลรวมจำนวนเลข 1 ทั้งหมดในก้อนข้อมูลเป็น เลขคู่ (เช่น ข้อมูล 1011001 มีเลข 1 อยู่ 4 ตัวซึ่งเป็นเลขคู่อยู่แล้ว จึงเติม Parity Bit = 0 กลายเป็น 10110010)
  • Odd Parity (พาริตีคี่): เติม 0 หรือ 1 เพื่อให้ผลรวมจำนวนเลข 1 ทั้งหมดเป็น เลขคี่
  • ข้อจำกัดร้ายแรง (จุดเน้นจากเลคเชอร์):
  1. ตรวจจับได้เฉพาะกรณีที่บิตเพี้ยนเป็นจำนวนคี่บิต (1, 3, 5 บิต): หากเกิด Impulse Noise ทำให้บิตเพี้ยนพร้อมกัน 2 บิต (จำนวนคู่) จำนวนเลข 1 จะยังคงเป็นเลขคู่เหมือนเดิม ทำให้ Parity Check ตรวจไม่พบความผิดพลาดเลย (ตรวจจับได้เพียง 50% ของกรณีทั้งหมด)
  2. ไม่สามารถระบุตำแหน่งบิตที่ผิด และแก้ไขข้อมูลเองไม่ได้ (ต้องขอให้ส่งใหม่สถานเดียว)

2.2 Cyclic Redundancy Check (CRC — มาตรฐานหลักใน Ethernet LAN และ Wi-Fi)

เพื่อแก้จุดอ่อนของ Parity Check เครือข่ายจริงจึงใช้ CRC (เช่น CRC-32 ใน Ethernet ที่ใช้ 32 บิตต่อท้ายเฟรมในช่อง FCS — Frame Check Sequence) ซึ่งมีความแม่นยำสูงมาก สามารถตรวจจับ Burst Error ได้เกือบ 100%

ที่มาที่ไปและเหตุผลเชิงวิศวกรรม (Why It Exists & First Principles)

หลักการทางคณิตศาสตร์ของ CRC (Binary Polynomial Modulo-2 Division): ต้นทางและปลายทางจะตกลงกันเลือก ตัวหารร่วมกัน 1 ตัว เรียกว่า Generator / Divisor ($G$) ที่มีความยาว $r+1$ บิต เป้าหมายคือการสร้างบิตส่วนเติมท้าย $R$ (ขนาด $r$ บิต) นำไปต่อท้ายข้อมูล $D$ เพื่อให้ก้อนข้อมูลทั้งหมดเมื่อนำไปหารแบบ Modulo-2 (การหารเลขฐานสองที่ใช้การ XOR แทนการลบ โดยไม่มีการยืมหลัก) ด้วยตัวหาร $G$ แล้ว ลงตัวพอดี (เศษเป็น 0)!

สมการและการคำนวณ (Mathematical Formulation & Step-by-Step Calculation)
ขั้นตอนการคำนวณ CRC ทีละสเต็ป (ฝึกคิดตามเพื่อใช้ในห้องสอบ):
สมมติข้อมูลต้นฉบับ D = 101110 (6 บิต) และตกลงใช้ตัวหาร G = 1001 (4 บิต -> ดังนั้น r = 4 - 1 = 3 บิต)

ขั้นที่ 1: เติมเลข 0 จำนวน r = 3 ตัว ต่อท้ายข้อมูล D ได้ตัวตั้งคือ: 101110000
ขั้นที่ 2: ตั้งหารยาวแบบใช้ XOR (บิตเหมือนกันได้ 0, บิตต่างกันได้ 1) ด้วยตัวหาร G = 1001:

        • ถ้าหารแล้วเหลือเศษไม่เป็นศูนย์ (Non-zero Remainder) แปลว่า "เกิด Bit Error ระหว่างทาง" ผู้รับจะทิ้งเฟรมนั้นทันที!

3. กลไกการควบคุมการไหลและการกู้คืนข้อผิดพลาด (Flow Control & ARQ Error Recovery)

เมื่อฝั่งผู้รับตรวจพบด้วย CRC ว่าเฟรมเสียหาย (หรือเฟรมสูญหายกลางทาง) ชั้น Data Link (และชั้น Transport) จะใช้กลไก ARQ (Automatic Repeat Request) ร่วมกับ Flow Control (การป้องกันไม่ให้ผู้ส่งส่งข้อมูลเร็วเกินกว่าที่บัฟเฟอร์ของผู้รับจะรับไหว) ซึ่งมีวิวัฒนาการ 3 รูปแบบ:

🏗️ เปรียบเทียบกลไกควบคุมความผิดพลาด ARQ ทั้ง 3 รูปแบบ (Stop-and-Wait, Go-Back-N, Selective Repeat)Architecture & Flow Diagram
1. Stop-and-Wait ARQทีละ 1 เฟรม
• Sender ส่ง Frame 0 ➜ หยุดรอจนกว่าจะได้รับ ACK 0 จึงส่ง Frame 1 ต่อได้
• หาก Frame 1 สูญหาย จะรอจน Timeout แล้วส่ง Frame 1 ซ้ำ
• ข้อสังเกต: เข้าใจง่ายแต่ท่อส่งข้อมูลว่างเปล่าขณะรอ ACK
2. Go-Back-N ARQส่งใหม่ยกชุด
• ส่งต่อเนื่องได้ N เฟรม โดยไม่ต้องหยุดรอทีละตัว
• ผู้รับไม่มี Buffer เก็บเฟรมข้ามลำดับ: หาก Frame 1 เสีย แม้ Frame 2, 3 จะมาถึงดี ผู้รับจะ โยน Frame 2, 3 ทิ้งทั้งหมด!
• ผู้ส่งต้องย้อนกลับไปส่งใหม่ยกชุดตั้งแต่ Frame 1, 2, 3
3. Selective Repeat ARQขอซ้ำเฉพาะตัวเสีย
• ผู้รับมี Buffer เก็บเฟรมที่มาก่อนลำดับ: หาก Frame 1 เสีย แต่ Frame 2 มาถึงดี ผู้รับจะ เก็บ Frame 2 ไว้ใน Buffer
• ส่งคำขอซ้ำเฉพาะเฟรมที่เสียตัวเดียว (SREJ 1)
• ประหยัดแบนด์วิดท์สูงสุด!

4. โปรโตคอลควบคุมการเข้าถึงสื่อกลาง (MAC Protocols) และคำถามสำคัญ: "ทำไม Slot Size ต้องเท่ากับ 512 bits?"

เมื่อคอมพิวเตอร์หลายเครื่องเชื่อมต่ออยู่บนสื่อกลางที่ใช้ร่วมกัน (Broadcast Shared Medium เช่น สายแลน Coaxial/Hub ในอดีต หรือคลื่นวิทยุ Wi-Fi/Cellular) หากสองเครื่องส่งข้อมูลพร้อมกัน สัญญาณจะผสมปนเปกันจนพังทั้งคู่ เรียกว่า การชนกันของข้อมูล (Collision) โปรโตคอล MAC จึงถูกแบ่งออกเป็น 3 ตระกูลใหญ่:

ตระกูลของโปรโตคอล MACหลักการแบ่งใช้ช่องสัญญาณตัวอย่างโปรโตคอลสำคัญ
1. Channel Partitioning<br>(การแบ่งซอยช่องสัญญาณตายตัว)แบ่งช่องสัญญาณออกเป็นส่วนย่อยๆ ให้แต่ละคนถือครองแยกกัน จึง ไม่มีวันเกิด Collision และรับประกันแบนด์วิดท์คงที่ แต่ถ้าใครไม่ส่งข้อมูล ช่องของคนนั้นจะว่างเปล่าสูญเปล่า• FDMA: แบ่งตามแถบความถี่ (Frequency)<br>• TDMA: แบ่งตามสล็อตเวลา (Time Slot)<br>• CDMA: แบ่งด้วยการคูณรหัสตั้งฉาก (Orthogonal Code) ส่งพร้อมกันบนความถี่เดียวกันได้
2. Taking Turns<br>(การผลัดกันส่งตามคิว)มีหัวหน้าคอยเรียกถามทีละเครื่อง หรือส่งไม้ผลัด (Token) วนไปรอบวง ใครถือ Token จึงมีสิทธิ์ส่ง• Polling Protocol (Master-Slave, Bluetooth)<br>• Token Ring / FDDI
3. Random Access<br>(การแย่งกันส่งแบบสุ่ม)ไม่มีการจองล่วงหน้า ใครมีข้อมูลให้ส่งด้วยความเร็วเต็มช่องสัญญาณ หากชนกันค่อยสุ่มเวลารอส่งใหม่ เหมาะกับทราฟฟิกคอมพิวเตอร์ที่มาเป็นพักๆ (Bursty Traffic)• Pure ALOHA (ส่งทันทีที่อยากส่ง, ประสิทธิภาพสูงสุดเพียง 18%)<br>• Slotted ALOHA (ส่งต้นสล็อตเวลา, ประสิทธิภาพเพิ่มเป็น 37%)<br>• CSMA/CD (ใช้ใน Ethernet แบบสาย)<br>• CSMA/CA (ใช้ใน Wireless LAN 802.11)

เจาะลึก CSMA/CD ใน Ethernet และที่มาของขนาดเฟรมขั้นต่ำ 512 บิต (64 ไบต์)

ในโปรโตคอล CSMA/CD (Carrier Sense Multiple Access with Collision Detection) ของ Ethernet มีกฎ 3 ข้อคือ: 1. ฟังก่อนส่ง (Carrier Sense - Listen before talk), 2. ขณะส่งก็ฟังไปด้วยว่ามีสัญญาณสวนมาชนหรือไม่ (Collision Detection - Listen while talking) และ 3. หากตรวจพบการชน ให้หยุดส่งทันที ส่งสัญญาณเตือน (Jam Signal) แล้วสุ่มเวลารอแบบ Binary Exponential Backoff

คำถามชวนคิดที่ เน้นย้ำในห้องเรียน: "ทำไมมาตรฐาน Ethernet (IEEE 802.3) จึงบังคับว่าทุกเฟรมต้องมีขนาดขั้นต่ำ (Minimum Frame Size / Slot Size) เท่ากับ 512 bits (หรือ 64 bytes)? ถ้าข้อมูลมีแค่ 10 ไบต์ ทำไมต้องยัดบิตเติม (Padding) ให้ครบ 64 ไบต์ก่อนส่ง?"

คำอธิบายที่มาที่ไปอย่างละเอียด: กลไก Collision Detection ของ CSMA/CD จะทำงานได้ถูกต้องก็ต่อเมื่อ "เครื่องผู้ส่ง (A) ต้องได้รับสัญญาณที่สะท้อนกลับมาจากเหตุการณ์ชนกัน ก่อนที่เครื่อง A จะส่งบิตสุดท้ายของเฟรมนั้นจบ!" เพราะถ้าเฟรมสั้นเกินไป เครื่อง A ส่งเฟรมจบไปแล้วและเข้าใจผิดว่าส่งสำเร็จแล้ว แต่สัญญาณเพิ่งวิ่งไปชนกับเครื่อง B ที่อยู่ปลายสายอีกฝั่งหนึ่ง เครื่อง A จะไม่รู้ตัวเลยว่าเฟรมนั้นพังและจะไม่ทำการส่งซ้ำ!

ในกรณีเลวร้ายที่สุด (Worst-case Scenario): เครื่อง A อยู่มุมซ้ายสุด และเครื่อง B อยู่มุมขวาสุด ห่างกันเป็นระยะทางสูงสุด $d_{\max}$ (เวลาที่สัญญาณเดินทางจาก A ไป B คือ $\tau = d_{\max}/v$) สมมติว่า A เริ่มส่งที่เวลา $t=0$ และในเสี้ยววินาทีสุดท้ายก่อนที่สัญญาณของ A จะไปถึง B (เวลา $t = \tau - \epsilon$) เครื่อง B เห็นว่าสายยังว่างจึงเริ่มส่งออกมาพอดี เกิดการชนกันที่หน้าบ้าน B แล้วคลื่นการชนต้องวิ่งย้อนกลับมาหา A อีก $\tau$ วินาที รวมเวลาไป-กลับสูงสุดเท่ากับ $2\tau$ (Round-Trip Propagation Delay)

สมการและการคำนวณ (Mathematical Formulation & Step-by-Step Calculation)
สมการพิสูจน์ขนาดเฟรมขั้นต่ำ (Minimum Frame Size / Slot Time):
  เวลาในการปล่อยเฟรม (Transmission Time: T_trans = L / R) ต้องมากกว่าหรือเท่ากับเวลาเดินทางไป-กลับสูงสุด (2 * τ):
    L / R  >=  2 * τ     ==>     L_min  =  2 * τ * R  =  2 * (d_max / v) * R

  ในมาตรฐาน 10 Mbps Ethernet (R = 10 × 10^6 bps):
  กำหนดเวลาเดินทางไป-กลับสูงสุดในสายแลนที่ผ่าน Repeater (Slot Time: 2τ) = 51.2 microseconds (51.2 × 10^-6 วินาที)
  ดังนั้น:
    L_min = (10 × 10^6 bits/sec) × (51.2 × 10^-6 sec)
          = 512 bits  (หาร 8 บิตต่อไบต์ = 64 Bytes พอดี!)

1. โครงสร้าง IPv4 Header และการแยกส่วนแพ็กเก็ต (IP Fragmentation)

ชั้น Network Layer (Layer 3) มีหน้าที่หลักในการส่งแพ็กเก็ตจากเครื่องต้นทางไปยังเครื่องปลายทางข้ามหลายเครือข่าย (Host-to-Host / End-to-End Delivery) โดยใช้โปรโตคอลหลักคือ IP (Internet Protocol) ซึ่งโครงสร้างส่วนหัวของ IPv4 Header มีขนาดมาตรฐาน 20 Bytes (หากไม่มี Options; และสูงสุดไม่เกิน 60 Bytes) โดยมีฟิลด์สำคัญที่ออกสอบในแล็บ Wireshark และข้อสอบปลายภาคดังนี้:

  • Protocol (8 bits): ระบุว่าข้อมูลข้างใน (Payload) จะส่งต่อไปให้โปรโตคอลใดที่ Layer 4 เช่น ICMP = 1, TCP = 6, UDP = 17

2. โครงสร้าง IPv4 Address, การแบ่ง Subnet (Subnetting), CIDR, NAT และ DHCP

2.1 โครงสร้าง IPv4 และช่วงหมายเลขพิเศษ (Special & Private IP Addresses)

หมายเลข IPv4 มีขนาด 32 บิต (4 ไบต์) เขียนในรูปเลขฐานสิบคั่นด้วยจุด (Dotted-Decimal Notation เช่น 192.168.1.1) แบ่งออกเป็น 2 ส่วนคือ Network Prefix (รหัสเครือข่าย) และ Host ID (รหัสเครื่อง) โดยมีหมายเลขพิเศษที่ต้องจำได้แม่นยำ:

  • Loopback Address (127.0.0.0/8 หรือ 127.0.0.1): ใช้สำหรับทดสอบโปรโตคอลเครือข่ายภายในเครื่องตัวเอง (Localhost) แพ็กเก็ตที่ส่งเข้าหมายเลขนี้จะไม่ถูกปล่อยออกไปที่การ์ดแลนจริง
  • Private IP Addresses (RFC 1918): หมายเลข IP ที่องค์กรสามารถนำมาตั้งซ้ำกันภายในเครือข่ายส่วนตัวได้ฟรีโดยไม่ต้องขออนุญาต (แต่ห้ามวิ่งออกไปบนอินเทอร์เน็ตสาธารณะโดยตรง):
  • 10.0.0.0/8 (10.0.0.0 – 10.255.255.255)
  • 172.16.0.0/12 (172.16.0.0 – 172.31.255.255)
  • 192.168.0.0/16 (192.168.0.0 – 192.168.255.255)

2.2 ทำไมต้องแบ่ง Subnet? (Subnetting vs Flat Network จากเลคเชอร์!)

ประเด็นเน้นย้ำในห้องเรียนโดยอาจารย์ผู้สอน (Classroom Lecture Insight)

อาจารย์เปรียบเทียบเครือข่ายที่ไม่มีการแบ่ง Subnet เลย (Flat Network) เสมือน "หมู่บ้านขนาดใหญ่ที่ไม่มีการแบ่งซอยและไม่มีเลขที่บ้านเป็นหมวดหมู่" ซึ่งมีข้อเสียร้ายแรงคือ: 1. บริหารจัดการและค้นหาปัญหา (Troubleshooting) ได้ยากมาก: เมื่อมีเครื่องปล่อยทราฟฟิกผิดปกติ จะหาต้นตอไม่เจอ 2. ไม่มีขอบเขตจำกัดความเสียหาย (No Security Boundary): หากเครื่องหนึ่งติดไวรัสหรือถูกโจมตี มันจะแพร่กระจายไปทั่วทั้งองค์กรทันที และเกิด Broadcast Storm ได้ง่าย

ดังนั้น การแบ่ง Subnet (เช่น แบ่งตามตึก ตามชั้น ตามแผนก หรือแยกกลุ่มอาจารย์ นักศึกษา และ Guest) จึงช่วยให้ 1. บริหารจัดการง่าย, 2. กำหนดนโยบายความปลอดภัยและกักกันโรค (Quarantine) ได้ที่ระดับ Router/Firewall, และ 3. ปิดบังโครงสร้างเครือข่ายภายในไม่ให้คนภายนอกเห็น

2.3 สูตรการคำนวณ Subnetting และ CIDR (Classless Inter-Domain Routing)

ในอดีตมีการแบ่งขนาดเครือข่ายแบบตายตัว (Classful Addressing: Class A /8, Class B /16, Class C /24) ซึ่งไม่ยืดหยุ่นและทำให้สูญเสียหมายเลข IP โดยเปล่าประโยชน์ ปัจจุบันจึงใช้มาตรฐาน CIDR (Classless Inter-Domain Routing) ที่กำหนดความยาวของ Network Prefix กี่บิตก็ได้ตามต้องการ (เช่น /22, /25, /26, /30) และช่วยทำ Route Aggregation (Supernetting) ยุบรวมหลายเส้นทางเข้าด้วยกันเพื่อให้ตาราง Routing Table ของอินเทอร์เน็ตมีขนาดเล็กลง

สมการและการคำนวณ (Mathematical Formulation & Step-by-Step Calculation)
สูตรการคำนวณจำนวน Host ใน Subnet (ต้องหักออก 2 IP เสมอ!):
  กำหนดให้เครือข่ายมี Prefix Length = /n (จากทั้งหมด 32 บิตของ IPv4)
  1. จำนวนบิตของฝั่ง Host (h) = 32 - n บิต
  2. จำนวนหมายเลข IP ทั้งหมดในวง = 2^h หมายเลข
  3. จำนวนเครื่องที่นำไปตั้งค่าใช้งานได้จริง (Valid Usable Hosts) = (2^h) - 2 หมายเลขเสมอ!
     • ทำไมต้องลบ 2 เสมอ?
       - หมายเลขแรกสุด (บิต Host เป็น 0 ทั้งหมด) จองไว้เป็น "Network Address" (ชื่อประจำวงเครือข่าย)
       - หมายเลขสุดท้าย (บิต Host เป็น 1 ทั้งหมด) จองไว้เป็น "Broadcast Address" (ใช้ส่งกระจายให้ทุกเครื่องในวง)
     • ข้อปฏิบัติในแล็บ: นิยมจอง Valid Host ตัวแรกสุด (เช่น .1) หรือตัวสุดท้าย (เช่น .254) ไว้เป็น Default Gateway ของ Router

ตัวอย่างการคำนวณ: วง 192.168.10.0/26
  • n = 26  ==>  จำนวนบิต Host (h) = 32 - 26 = 6 บิต
  • จำนวน IP ทั้งหมดต่อวง = 2^6 = 64 หมายเลข (ขนาดบล็อกทีละ 64)
  • จำนวน Valid Hosts ที่ใช้ได้จริง = 64 - 2 = 62 เครื่อง
  • Subnet ที่ 1: Network = 192.168.10.0 | Valid Hosts = 192.168.10.1 ถึง .62 | Broadcast = 192.168.10.63

2.4 เทคโนโลยียืดอายุ IPv4: NAT และ DHCP

แม้หมายเลข IPv4 ทั้งโลกจะมีเพียง $2^{32} \approx 4.29$ พันล้านหมายเลขและถูกจัดสรรหมดไปแล้ว แต่เรายังใช้งาน IPv4 ได้จนถึงทุกวันนี้เพราะ 2 เทคโนโลยีคู่บุญ:

  1. DHCP (Dynamic Host Configuration Protocol): แจกจ่ายหมายเลข IP, Subnet Mask, Default Gateway และ DNS Server ให้เครื่องลูกข่ายแบบอัตโนมัติและชั่วคราว (Lease Time) ผ่านกระบวนการ 4 ขั้นตอน DORA (DHCP Discover ➔ DHCP Offer ➔ DHCP Request ➔ DHCP ACK) ทำให้ไม่ต้องล็อกหมายเลข IP ทิ้งไว้กับเครื่องที่ปิดอยู่
  2. NAT (Network Address Translation / NAPT): ให้เครื่องภายในองค์กรนับพันเครื่องใช้หมายเลข Private IP แล้วเมื่อต้องการออกสู่อินเทอร์เน็ต เราเตอร์ตัวหน้าบ้านจะแปลง Private IP เหล่านั้นให้ใช้ Public IP เพียงหมายเลขเดียวร่วมกัน (Many-to-One Mapping) โดยใช้ หมายเลขพอร์ต (Port Number 16-bit) ในตาราง NAT Translation Table เป็นตัวแยกแยะว่าคำตอบที่วิ่งกลับมานั้นเป็นของเครื่องใดภายในบ้าน

3. วิวัฒนาการสู่ IPv6 และคำถามสำคัญ: "ทำไมจึงข้ามจาก IPv4 ไปเป็น IPv6 โดยไม่มี IPv5?"

ประเด็นเน้นย้ำในห้องเรียนโดยอาจารย์ผู้สอน (Classroom Lecture Insight)

เฉลยคำถามชวนคิด ในห้องเรียน: "ทำไมเราจึงเปลี่ยนจาก IPv4 ข้ามไปเป็น IPv6 เลย? IPv5 หายไปไหน?"

• คำตอบ: ในความเป็นจริง หมายเลขเวอร์ชัน 5 ในช่อง Version ของ IP Header ถูกจองและใช้งานไปแล้วตั้งแต่ปี ค.ศ. 1979 สำหรับโปรโตคอลทดลองชื่อว่า ST (Internet Stream Protocol — RFC 1190 / RFC 1819) ซึ่งออกแบบมาเพื่อทดลองส่งข้อมูลเสียงและวิดีโอแบบสตรีมมิ่งตามเวลาจริงแต่ไม่ได้ถูกนำมาใช้แทน IPv4 ดังนั้นเมื่อคณะทำงาน IETF ออกแบบโปรโตคอลรุ่นใหม่เพื่อแก้ปัญหา IP หมดอย่างถาวรในทศวรรษ 1990 จึงต้องข้ามเลข 5 ที่ถูกจองไปแล้ว ไปใช้หมายเลข 6 (IPv6) นั่นเอง!

จุดเด่นและการเปลี่ยนแปลงเชิงสถาปัตยกรรมของ IPv6 (เปรียบเทียบกับ IPv4)

  1. ขนาดที่อยู่ใหญ่มหาศาล (128 bits): เพิ่มจาก 32 บิตใน IPv4 เป็น 128 บิต ($2^{128} \approx 3.4 \times 10^{38}$ หมายเลข) เขียนในรูป เลขฐานสิบหก (Hexadecimal) จำนวน 8 กลุ่ม กลุ่มละ 4 ตัวอักษร คั่นด้วยเครื่องหมายโคลอน (:) เช่น 2601:0193:8302:4620:215c:f5ae:8b40:a27a
  • กฎการย่อรูป IPv6: สามารถตัดเลข 0 นำหน้าของแต่ละกลุ่มออกได้ (เช่น 0193 ย่อเป็น 193) และหากมีกลุ่มที่เป็น 0000 ติดกันหลายกลุ่ม สามารถยุบรวมเป็นเครื่องหมาย :: (Double Colon) ได้เพียง 1 ครั้งในที่อยู่นั้น (เช่น fe80:0000:0000:0000:1085:6434:0583:0e79 ย่อเป็น fe80::1085:6434:583:e79)
  1. ส่วนหัวขนาดคงที่ 40 Bytes (Fixed 40-Byte Header) เพื่อการประมวลผลความเร็วสูง:
  • ตัด Header Checksum ทิ้ง: เพื่อไม่ต้องให้เราเตอร์ทุกตัวเสียเวลาคำนวณ Checksum ใหม่ทุกครั้งที่ลดค่า Hop Limit (ปล่อยให้ Layer 2 CRC และ Layer 4 TCP/UDP Checksum ดูแลแทน)
  • ตัดการทำ Fragmentation โดยเราเตอร์ระหว่างทางทิ้ง: เราเตอร์ IPv6 จะไม่หั่นแพ็กเก็ตกลางทางอีกต่อไป (ทำได้ที่เครื่องต้นทางเท่านั้น) เพื่อเพิ่มความเร็วการส่งต่อแพ็กเก็ต
  • เพิ่มฟิลด์ Flow Label (20 bits): สำหรับระบุกระแสข้อมูลพิเศษที่ต้องการคุณภาพการให้บริการ (QoS / Real-time streaming) และใช้ฟิลด์ Next Header แทนฟิลด์ Protocol เดิม

1. การแยกหน้าที่สำคัญของ Network Layer: Forwarding vs Control Plane

ในการทำงานของเราเตอร์ทุกตัว จะมีหน้าที่หลัก 2 ส่วนที่ต้องแยกให้ออก:

  1. Forwarding (Data Plane — การส่งต่อแพ็กเก็ตในระดับท้องถิ่น): เมื่อแพ็กเก็ตวิ่งเข้ามาที่พอร์ตขาเข้า เราเตอร์จะเปิดดูตาราง Forwarding Table ในเครื่องตัวเองแล้วส่งแพ็กเก็ตออกไปยังพอร์ตขาออกที่ถูกต้องทันที (ใช้เวลาระดับนาโนวินาที ทำด้วยฮาร์ดแวร์)
  2. Routing (Control Plane — มันสมองในการคำนวณเส้นทางระดับเครือข่าย): กระบวนการที่คำนวณว่าจากต้นทางไปปลายทางควรวิ่งผ่านเราเตอร์ตัวใดบ้างจึงจะสั้นและดีที่สุด แล้วนำผลลัพธ์ที่ได้ไปเขียนลงใน Forwarding Table โดยสถาปัตยกรรมของ Control Plane แบ่งออกเป็น 2 ยุค:
  • ยุคที่ 1 — Per-Router Control Plane (Distributed / Traditional Routing): เราเตอร์ทุกตัวมีสมองของตัวเอง รันอัลกอริทึมแลกเปลี่ยนข้อมูลกับเราเตอร์ตัวอื่นเพื่อคำนวณตารางเส้นทางของใครของมัน (เช่น RIP, OSPF, EIGRP, BGP)
  • ยุคที่ 2 — Logically Centralized Control Plane (Software-Defined Networking - SDN): แยก "มันสมอง" ออกจากตัวเราเตอร์ ไปรวมศูนย์ไว้ที่เซิร์ฟเวอร์กลางที่เรียกว่า SDN Controller เพียงจุดเดียว ส่วนสวิตช์/เราเตอร์ทำหน้าที่เป็นเพียงอุปกรณ์ส่งต่อข้อมูลตามคำสั่ง

2. ทฤษฎีกราฟและการเปรียบเทียบ Link-State (Dijkstra) vs Distance-Vector (Bellman-Ford)

ในมุมมองคณิตศาสตร์ เครือข่ายคอมพิวเตอร์คือ กราฟ $G = (N, E)$ โดยเซตของโหนด $N$ คือเราเตอร์ทั้งหมด และเซตของเส้นเชื่อม $E$ คือลิงก์เชื่อมต่อที่มีค่าใช้จ่าย (Cost / Metric เช่น ระยะทาง, เวลาหน่วง Delay, หรือส่วนกลับของแบนด์วิดท์) อัลกอริทึมการหาเส้นทางที่สั้นที่สุดแบ่งออกเป็น 2 ค่ายหลัก:

  • นำโหนด $w$ ที่เพิ่งเลือก มาอัปเดตระยะทางไปยังเพื่อนบ้าน $v$ ทุกตัวของ $w$ ตามสูตรผ่อนคลาย (Relaxation):

3. การจัดลำดับชั้นเครือข่าย (Autonomous Systems): Intra-AS vs Inter-AS Routing

อินเทอร์เน็ตทั่วโลกมีเราเตอร์หลายร้อยล้านตัว หากให้เราเตอร์ทุกตัวต้อง Flood LSP หากันทั่วโลก ตาราง Routing Table จะระเบิดและเครือข่ายจะล่มทันที จึงต้องจัดโครงสร้างเป็นลำดับชั้น (Hierarchical Routing) โดยแบ่งเครือข่ายออกเป็นเขตปกครองตนเองที่เรียกว่า AS (Autonomous System — เครือข่ายที่อยู่ภายใต้การดูแลขององค์กรหรือ ISP เดียวกัน):

  1. Intra-AS Routing (Interior Gateway Protocols - IGP): การหาเส้นทาง ภายใน AS เดียวกัน
  • เป้าหมายหลัก: เน้นประสิทธิภาพและความเร็วสูงสุด (Performance / Shortest Path) ไม่ต้องกังวลเรื่องนโยบายการเมืองระหว่างองค์กร
  • โปรโตคอลสำคัญ:
  • RIP (Routing Information Protocol): ใช้แบบ Distance-Vector นับจำนวนก้าว (Hop Count สูงสุดไม่เกิน 15 hops ถ้าถึง 16 ถือว่าไปไม่ถึง)
  • OSPF (Open Shortest Path First): ใช้แบบ Link-State (Dijkstra) คำนวณ Cost จากแบนด์วิดท์ของลิงก์ ($Cost = \text{Reference Bandwidth} / \text{Interface Bandwidth}$) รองรับการแบ่งเป็นลำดับชั้นย่อย (Area 0 Backbone)
  • EIGRP: โปรโตคอลขั้นสูงที่พัฒนาโดย Cisco ผสานข้อดีของ DV และ LS เข้าด้วยกัน
  1. Inter-AS Routing (Exterior Gateway Protocol - EGP): การหาเส้นทาง เชื่อมระหว่าง AS ต่างองค์กรกัน
  • เป้าหมายหลัก: เน้นเรื่องนโยบายและข้อตกลงทางธุรกิจ (Policy-Based Routing) มากกว่าความสั้นของระยะทาง เช่น "ISP A ยอมให้ทราฟฟิกของลูกค้าตัวเองวิ่งผ่าน แต่ไม่ยอมเป็นทางผ่านฟรี (Transit) ให้ทราฟฟิกของคู่แข่ง"
  • โปรโตคอลมาตรฐานหนึ่งเดียวของอินเทอร์เน็ต: BGP (Border Gateway Protocol) แบ่งเป็น eBGP (คุยข้าม AS) และ iBGP (กระจายข้อมูลเส้นทางภายนอกให้เราเตอร์ภายใน AS ตัวเองรับทราบ)

4. สถาปัตยกรรมเครือข่ายสมัยใหม่: Software-Defined Networking (SDN) และ OpenFlow (จุดเน้นจากเลคเชอร์!)

ประเด็นเน้นย้ำในห้องเรียนโดยอาจารย์ผู้สอน (Classroom Lecture Insight)

จากการบรรยายของอาจารย์เรื่อง Traditional Routing vs Software-Defined Networking (SDN) อาจารย์ได้ชี้ให้เห็นข้อจำกัด 4 ประการของการทำ Routing แบบดั้งเดิม (Per-Hop Distributed): 1. ความไม่ยืดหยุ่นในการบังคับเส้นทาง (Rigidity): ในโปรโตคอลแบบเดิมอย่าง OSPF หากเราต้องการแบ่งทราฟฟิกครึ่งหนึ่งไปทางซ้าย และอีกครึ่งไปทางขวา หรือต้องการให้ทราฟฟิกแผนกบัญชีวิ่งอ้อมไปผ่าน Firewall เสมอ ทำได้ยากมาก เพราะอัลกอริทึมถูกฝังมาให้เลือกเฉพาะเส้นทางที่ Cost ต่ำสุดเพียงเส้นเดียว 2. การแพร่กระจายความผิดพลาด (Error Propagation): ใน Distance-Vector หากเราเตอร์ตัวหนึ่งตั้งค่าผิดหรือคำนวณผิด ข้อมูลที่ผิดจะแพร่กระจายไปทำลายตารางของเพื่อนบ้านทั้งเครือข่าย (เช่น Count-to-infinity) 3. การผูกขาดยี่ห้อ (Proprietary Vendor Lock-in): ฮาร์ดแวร์และซอฟต์แวร์ควบคุมถูกมัดรวมอยู่ในกล่องเราเตอร์ยี่ห้อนั้นๆ 4. เหตุผลในอดีตที่ทำ Centralized ไม่ได้: สมัยก่อนแบนด์วิดท์เครือข่ายต่ำและซีพียูช้า การส่งข้อมูลทุกอย่างมาคำนวณที่ศูนย์กลางจึงเป็นไปไม่ได้ แต่ในปัจจุบันแบนด์วิดท์และพลังประมวลผลสูงมากแล้ว จึงเกิดเป็น SDN!

  • ความท้าทายสำคัญของ SDN: เนื่องจากสมองรวมอยู่ที่จุดเดียว ตัว SDN Controller จึงเสี่ยงต่อการเป็น Single Point of Failure และเป็นเป้าหมายหลักของแฮกเกอร์ จึงต้องออกแบบให้มี High Availability (Distributed Controller Cluster) และวาง Security by Design ตั้งแต่วันแรก (Day One)

1. บทบาทของ Transport Layer และการเปรียบเทียบ UDP vs TCP

ขณะที่ Network Layer ส่งข้อมูลจากเครื่องถึงเครื่อง (Host-to-Host) ชั้น Transport Layer (Layer 4) มีหน้าที่รับผิดชอบการส่งข้อมูลจาก โปรเซสของแอปพลิเคชันต้นทาง ไปยังโปรเซสของแอปพลิเคชันปลายทาง (Process-to-Process Delivery) โดยใช้ Port Number (16 bits: 0–65535) เป็นตัวระบุห้องปลายทาง โดยมีโปรโตคอลหลัก 2 ตัวที่มีปรัชญาตรงข้ามกัน:

คุณสมบัติเปรียบเทียบUDP (User Datagram Protocol)TCP (Transmission Control Protocol)
1. รูปแบบการเชื่อมต่อConnectionless (ไร้การเชื่อมต่อ): ส่งข้อมูลออกไปทันทีโดยไม่ทักทายสร้างการเชื่อมต่อล่วงหน้า (No Handshake)Connection-Oriented: ต้องสร้างการเชื่อมต่อด้วย 3-Way Handshake (SYN ➔ SYN+ACK ➔ ACK) ก่อนส่งข้อมูลเสมอ

3. การควบคุมการไหลและความแออัดไม่มี ทั้ง Flow Control และ Congestion Control (แอปพลิเคชันอยากส่งเร็วแค่ไหนก็ปล่อยออกไปทันที)มีครบถ้วน: มีทั้ง Flow Control (Advertised Window) และ Congestion Control (Congestion Window)

2. การประเมินเวลา RTT และการตั้งค่า RTO (Retransmission Timeout) — ออกสอบข้อที่ 1 ในข้อสอบ Final!

จุดออกสอบและกับดักที่ต้องระวัง (Exam Focus & Common Pitfalls)

เนื้อหาตรงกับข้อสอบ Final ข้อที่ 1 (4 คะแนน): เมื่อ TCP ส่ง Segment ออกไป มันจะเริ่มจับเวลาถอยหลังที่เรียกว่า RTO (Retransmission Timeout) หากเวลานับถอยหลังจนหมดแล้วยังไม่ได้รับ ACK ตอบกลับ TCP จะสรุปว่าแพ็กเก็ตสูญหายและทำการส่งซ้ำทันที คำถามคือ "เราควรตั้งค่า RTO เท่าไหร่จึงจะเหมาะสม?"

🏗️ กราฟเปรียบเทียบการตั้งค่า TCP Retransmission Timeout (RTO) เทียบกับค่า Sampled RTT จริงArchitecture & Flow Diagram

สรุปผลกระทบของการตั้งค่า RTO และวิธีการกำหนดค่า RTO ที่ดี (ใช้ตอบข้อสอบข้อ 1.1, 1.2, 1.3):

  1. กรณีที่ 1 (ข้อ 1.1): หากกำหนดค่า RTO เป็นค่าคงที่ที่ต่ำเกินไป (เช่น RTO = 3 ms ซึ่งต่ำกว่าค่า Sampled RTT ในหลายช่วงเวลา) จะเกิดอะไรขึ้น?
  • คำตอบ: ในช่วงที่เครือข่ายมีความหน่วงปกติทำให้ค่า Sampled RTT สูงเกินกว่า 3 ms (เช่น ใช้เวลาเดินทางจริง 4–6 ms) แพ็กเก็ตและ ACK ยังไม่ได้สูญหายแต่อย่างใด (เพียงแต่กำลังเดินทางกลับมา) แต่ตัวจับเวลา RTO ของผู้ส่งจะหมดเวลาเสียก่อน (Premature Timeout) ส่งผลให้ผู้ส่งเข้าใจผิดว่าแพ็กเก็ตหาย จึงทำการ ส่งแพ็กเก็ตซ้ำโดยไม่จำเป็น (Unnecessary / Spurious Retransmissions) ซึ่งนอกจากจะสิ้นเปลืองแบนด์วิดท์โดยเปล่าประโยชน์แล้ว ยังเป็นการเติมแพ็กเก็ตซ้ำซ้อนเข้าไปซ้ำเติมให้เครือข่ายเกิดความแออัด (Congestion) หนักขึ้น และทำให้ TCP ลดขนาด Congestion Window ลงโดยไม่จำเป็นอีกด้วย!
  1. กรณีที่ 2 (ข้อ 1.2): หากกำหนดค่า RTO เป็นค่าคงที่ที่สูงเกินไป (เช่น RTO = 8 ms ซึ่งสูงกว่า Sampled RTT ปกติมาก) จะเกิดอะไรขึ้น?
  • คำตอบ: เมื่อเกิดเหตุการณ์ แพ็กเก็ตสูญหายจริงในเครือข่าย (Packet Loss) แทนที่ผู้ส่งจะตรวจพบและส่งซ้ำได้อย่างรวดเร็ว ผู้ส่งจะต้องนั่งรอไปจนครบเวลา 8 ms จึงจะเริ่มส่งแพ็กเก็ตซ้ำ ทำให้ การกู้คืนข้อมูลที่สูญหายล่าช้ามาก (Slow Loss Recovery / Long Idle Delay) ส่งผลให้เกิดความหน่วงสูง (High Latency) และทำให้อัตราการส่งข้อมูลรวม (Throughput) ของระบบลดต่ำลง
  1. กรณีที่ 3 (ข้อ 1.3): จงอธิบายวิธีการกำหนดค่า RTO ที่ดี:
  • คำตอบ: ค่า RTO ที่ดี ไม่ควรตั้งเป็นค่าคงที่ตายตัว (Static) แต่ต้องปรับตัวแบบไดนามิก (Adaptive / Dynamic RTO) ตามสภาพของเครือข่ายในแต่ละ Session โดยต้องคำนวณจาก 1) ค่าเฉลี่ยถ่วงน้ำหนักของเวลารอบเดินทาง (EstimatedRTT) บวกกับ 2) ค่าความแปรปรวนหรือส่วนเบี่ยงเบนของ RTT (DevRTT / RTT Variance) คูณด้วยค่าคงที่ปลอดภัย (ตามสมการของ Jacobson/Karels: $\text{RTO} = \text{EstimatedRTT} + 4 \times \text{DevRTT}$) เพื่อให้ค่า RTO อยู่เหนือค่า RTT จริงเล็กน้อยเสมอและสามารถขยายตัวครอบคลุมช่วงที่ความหน่วงของเครือข่ายแกว่งตัวสูงขึ้นได้โดยไม่เกิด Premature Timeout
สมการและการคำนวณ (Mathematical Formulation & Step-by-Step Calculation)
สมการคำนวณ Adaptive RTO มาตรฐานของ TCP (RFC 6298):
  1. คำนวณค่าเฉลี่ยถ่วงน้ำหนัก (Exponential Weighted Moving Average - EWMA, โดยปกติ α = 0.125):
     EstimatedRTT = (1 - α) × EstimatedRTT_เดิม  +  α × SampleRTT_ล่าสุด

  2. คำนวณค่าความแปรปรวน (RTT Deviation / Variance, โดยปกติ β = 0.25):
     DevRTT = (1 - β) × DevRTT_เดิม  +  β × | SampleRTT_ล่าสุด - EstimatedRTT |

  3. กำหนดค่า Timeout (RTO):
     RTO = EstimatedRTT + 4 × DevRTT

3. กลไกควบคุมการไหลและควบคุมความแออัดของ TCP (Flow Control vs Congestion Control) — ออกสอบข้อที่ 3!

ในการส่งข้อมูลของ TCP ผู้ส่งจะถูกจำกัดปริมาณข้อมูลที่ส่งออกไปได้โดยยังไม่ต้องรอ ACK ด้วยหน้าต่าง 2 บานเสมอ คือ: $$\text{Effective Window} = \min(\text{Advertised Window } [rwnd], \text{ Congestion Window } [cwnd])$$

  1. Advertised Window (rwnd — Receive Window) [ออกสอบข้อ 3.1]:
  • คืออะไร: คือขนาดหน้าต่างรับข้อมูลที่ ฝั่งผู้รับปลายทาง (Receiver / Destination) แจ้งกลับมาบอกฝั่งผู้ส่ง (ในช่อง Window Size ของ TCP Header) เพื่อระบุว่าขณะนี้บัฟเฟอร์หน่วยความจำของฝั่งผู้รับยังเหลือพื้นที่ว่างรองรับข้อมูลได้อีกกี่ไบต์
  • มีไว้ทำไม: ใช้สำหรับทำ Flow Control (การควบคุมการไหล) เพื่อป้องกันไม่ให้ฝั่งผู้ส่งที่เครื่องแรงกว่า ส่งข้อมูลเร็วเกินไปจนล้นบัฟเฟอร์ของฝั่งผู้รับ (Prevent Receiver Buffer Overflow)
  1. Congestion Window (cwnd) และกลไก TCP Slow Start [ออกสอบข้อ 3.2]:
  • Congestion Window (cwnd) คืออะไร: คือขนาดหน้าต่างที่ ฝั่งผู้ส่ง (Sender) ประเมินและคำนวณขึ้นเองเพื่อจำกัดอัตราการส่งข้อมูลไม่ให้ท่วมท้นเกินขีดความสามารถของเราเตอร์และลิงก์ในเครือข่าย (Network Congestion Control)
  • กลไก TCP Slow Start ช่วยเพิ่มประสิทธิภาพของการส่งข้อมูลอย่างไร (คำตอบสำหรับข้อ 3.2):
  • เมื่อเริ่มต้นการเชื่อมต่อ TCP ใหม่ ผู้ส่งยังไม่ทราบเลยว่าเครือข่ายระหว่างทางมีแบนด์วิดท์ว่างมากน้อยเพียงใด หากส่งข้อมูลก้อนใหญ่โครมเดียวทันทีอาจทำให้เราเตอร์ล่ม แต่หากค่อยๆ เพิ่มทีละ 1 MSS แบบเส้นตรง (Additive Increase) ก็จะใช้เวลานานมากในการไต่ระดับไปถึงความจุของเครือข่ายความเร็วสูง
  • ดังนั้น Slow Start จึงเริ่มต้นที่ค่าปลอดภัยคือ cwnd = 1 MSS แต่เมื่อได้รับ ACK กลับมาแต่ละรอบ RTT มันจะ เพิ่มขนาด cwnd แบบทวีคูณเป็น 2 เท่าทุกๆ 1 RTT (1 ➔ 2 ➔ 4 ➔ 8 ➔ 16 ➔ 32... Exponential Growth)
  • ประโยชน์: ช่วยให้ TCP สามารถสำรวจและไต่ระดับขึ้นไปถึงขีดความสามารถในการรองรับข้อมูลของเครือข่าย (Available Network Capacity / ssthresh) ได้อย่าง รวดเร็วที่สุดโดยไม่สร้างภาระกระแทกเครือข่ายตั้งแต่ต้น ก่อนที่จะสลับเข้าสู่โหมด Congestion Avoidance (AIMD — เพิ่มแบบเส้นตรงทีละ 1 MSS ต่อ RTT) เพื่อให้ส่งข้อมูลได้อย่างมีเสถียรภาพ

4. กลไกการหลีกเลี่ยงความแออัดโดยเราเตอร์: DECbit และ Random Early Detection (RED) — ออกสอบข้อที่ 2!

ประเด็นเน้นย้ำในห้องเรียนโดยอาจารย์ผู้สอน (Classroom Lecture Insight)

จากการบรรยายเรื่อง กลไกการควบคุมความแออัดของ TCP และเทคนิคการหลีกเลี่ยงความแออัด (Congestion Avoidance) อาจารย์ได้ชี้ให้เห็นว่า:

• ลำพังกลไกของ TCP ที่ฝั่ง Host เป็นการแก้ปัญหาแบบ "วัวหายล้อมคอก" (Reactive): คือต้องรอให้คิวในเราเตอร์เต็มจนแพ็กเก็ตถูกทิ้ง (Tail Drop) เกิดความเสียหายขึ้นแล้ว ต้นทางจึงค่อยลดความเร็วลง ทำให้กราฟความเร็วเป็นฟันเลื่อย ไม่ราบรื่น และเกิดปัญหา Global Synchronization (ทุก Session โดน Drop พร้อมกันจึงลดความเร็วพร้อมกันและเร่งกลับมาชนกันใหม่พร้อมกัน)

• เนื่องจาก Router เป็นจุดที่เห็นความยาวคิวและรับรู้สถานะความแออัดได้ดีที่สุด จึงมีการคิดค้นกลไก Active Queue Management (AQM) ให้เราเตอร์ช่วยแจ้งเตือนหรือจัดการก่อนที่คิวจะเต็มล้น 2 วิธีหลัก:

  1. กลไก DECbit (Explicit Congestion Notification):
  • เราเตอร์คำนวณความยาวคิวเฉลี่ย หากเกินเกณฑ์ เราเตอร์จะตั้งค่า บิตแจ้งเตือนความแออัด (DECbit = 1) ในส่วนหัวของแพ็กเก็ต
  • เมื่อแพ็กเก็ตไปถึงผู้รับ ผู้รับจะคัดลอกบิตนี้ใส่ใน ACK ส่งกลับมาบอกผู้ส่ง
  • ผู้ส่งจะนับสัดส่วนแพ็กเก็ตที่มีบิตแจ้งเตือนในรอบ Window ที่ผ่านมา: หากน้อยกว่า 50% จะเพิ่มความเร็วทีละ 1 (Additive Increase) แต่ หากตั้งแต่ 50% ขึ้นไป จะลดขนาด Window ลงทันที (Multiplicative Decrease คูณ 0.875)
  1. กลไก Random Early Detection (RED):
  • แทนที่จะใช้บิตพิเศษ เราเตอร์ที่ใช้ RED จะคำนวณ ค่าเฉลี่ยถ่วงน้ำหนักตามเวลาของความยาวคิว (AvgLen — Time-Averaged Queue Length) แทนการใช้ค่าความยาวคิว ณ เสี้ยววินาทีนั้น (Snapshot) เพื่อป้องกันไม่ให้เราเตอร์ตกใจเกินจริงเมื่อมีข้อมูลพุ่งเข้ามาเพียงชั่ววูบสั้นๆ (Transient Burst)
  • เมื่อค่า AvgLen เริ่มสูงเกินขีดจำกัดขั้นต่ำ (MinThreshold) เราเตอร์จะเริ่ม สุ่มดรอปแพ็กเก็ต (Randomly Drop Packet) ตามความน่าจะเป็น $P_{\text{drop}}$ เพื่อส่งสัญญาณเตือนให้บาง TCP Session ค่อยๆ ลดความเร็วลงก่อนที่คิวจะเต็มจริง ช่วยให้เกิด Desynchronization (แต่ละ Session ลดความเร็วไม่พร้อมกัน ภาพรวมทราฟฟิกจึงราบรื่น) และใครที่ส่งข้อมูลเข้ามามากก็จะมีโอกาสถูกสุ่มดรอปมากกว่าตามสัดส่วน

วิธีอ่านกราฟ RED และคำนวณเปอร์เซ็นต์ $P_{\text{Throughput}}$ (ตรงกับข้อสอบ Final ข้อที่ 2 เป๊ะ!)

ในข้อสอบ Final ข้อที่ 2 โจทย์กำหนดกราฟความน่าจะเป็นในการดรอปแพ็กเก็ต ($P_{\text{drop}}$ บนแกนตั้ง) เทียบกับค่าความยาวคิวเฉลี่ย ($\text{AvgLen}$ บนแกนนอน) จำนวน 2 กราฟ คือ RED-1 และ RED-2 โดยมีพารามิเตอร์บนกราฟดังนี้:

  • ขีดจำกัดเริ่มต้น ($\text{MinThreshold}$) = 10 packets และขีดจำกัดสูงสุด ($\text{MaxThreshold}$) = 15 packets
  • ในกราฟ RED-1: ที่ $\text{AvgLen} = 10$ ค่า $P_{\text{drop}} = 0$ และไต่ขึ้นเป็นเส้นตรงไปถึงจุด $\text{AvgLen} = 15$ ซึ่งมีค่า $P_{\text{drop}} = 0.5$ (หรือ 50%) จากนั้นเมื่อ $\text{AvgLen} > 15$ ค่า $P_{\text{drop}}$ จะกระโดดขึ้นเป็น $1.0$ (ดรอป 100%)
  • ในกราฟ RED-2: ที่ $\text{AvgLen} = 10$ ค่า $P_{\text{drop}} = 0$ และไต่ขึ้นเป็นเส้นตรงไปถึงจุด $\text{AvgLen} = 15$ ซึ่งมีค่า $P_{\text{drop}} = 0.7$ (หรือ 70%) จากนั้นเมื่อ $\text{AvgLen} > 15$ ค่า $P_{\text{drop}}$ จะกระโดดขึ้นเป็น $1.0$ (ดรอป 100%)
สมการและการคำนวณ (Mathematical Formulation & Step-by-Step Calculation)
สูตรหัวใจสำคัญในการทำข้อสอบข้อที่ 2:
  โจทย์ถามหา P_Throughput (เปอร์เซ็นต์ของแพ็กเก็ตที่รอดชีวิตวิ่งออกจาก Router ต่อจำนวนที่เข้ามาทั้งหมด)
  ไม่ใช่ถาม P_drop! ดังนั้นต้องลบออกจาก 1 (หรือ 100%) เสมอ:

    P_Throughput = (1 - P_drop) × 100%

  และในช่วงเส้นลาดเอียงระหว่าง MinTh (10) ถึง MaxTh (15) คำนวณ P_drop ด้วยสมการเส้นตรง (Linear Interpolation):
    P_drop(AvgLen) = P_max × (AvgLen - MinTh) / (MaxTh - MinTh)
                   = P_max × (AvgLen - 10) / (15 - 10)
                   = P_max × (AvgLen - 10) / 5

  แทนค่าทั้ง 4 ข้อย่อยของข้อสอบ:
  • ข้อ 2.1) AvgLen = 10 packets, ใช้ RED-2:
    ที่ AvgLen = 10 (ยังไม่เกิน MinTh) ค่า P_drop = 0
    ดังนั้น P_Throughput = (1 - 0) × 100% = 100%

  • ข้อ 2.2) AvgLen = 18 packets, ใช้ RED-1:
    ที่ AvgLen = 18 (สูงเกิน MaxTh ที่ 15 ไปแล้ว) คิวอยู่ในโซนวิกฤต เราเตอร์จะ Drop ทุกแพ็กเก็ต (P_drop = 1.0 หรือ 100%)
    ดังนั้น P_Throughput = (1 - 1.0) × 100% = 0%

  • ข้อ 2.3) AvgLen = 13 packets, ใช้ RED-1 (ซึ่งมี P_max = 0.5 ที่จุด 15):
    P_drop = 0.5 × (13 - 10) / (15 - 10) = 0.5 × (3 / 5) = 0.30 (ดรอป 30%)
    ดังนั้น P_Throughput = (1 - 0.30) × 100% = 70%

  • ข้อ 2.4) AvgLen = 13 packets, ใช้ RED-2 (ซึ่งมี P_max = 0.7 ที่จุด 15):
    P_drop = 0.7 × (13 - 10) / (15 - 10) = 0.7 × (3 / 5) = 0.42 (ดรอป 42%)
    ดังนั้น P_Throughput = (1 - 0.42) × 100% = 58%

1. สถาปัตยกรรมแอปพลิเคชันเครือข่าย: Client-Server vs P2P vs Hybrid

ในการออกแบบโปรแกรมประยุกต์บนเครือข่ายที่ชั้น Application Layer (Layer 7) มีรูปแบบสถาปัตยกรรมหลัก 3 รูปแบบ:

  1. Client-Server Architecture: มีเครื่องเซิร์ฟเวอร์กลางที่เปิดทำงานตลอดเวลา (Always-on Host) และมีหมายเลข IP ถาวร คอยรอรับคำขอจากเครื่องลูกข่าย (Clients) ซึ่งไม่คุยกันเองโดยตรง (ตัวอย่าง: Web HTTP, อีเมล, DNS)
  2. Pure Peer-to-Peer (P2P) Architecture: ไม่มีเซิร์ฟเวอร์กลางที่เปิดตลอดเวลา เครื่องของผู้ใช้ทั่วไปแต่ละเครื่อง (Peers) เชื่อมต่อและแลกเปลี่ยนไฟล์กันโดยตรง ข้อดีคือขยายขนาดตัวเองได้อัตโนมัติ (Self-Scalability: ยิ่งมีคนเข้ามาดาวน์โหลดมาก ก็ยิ่งมีคนช่วยอัปโหลดมากขึ้น) แต่จัดการความปลอดภัยยากเนื่องจากเครื่องเปลี่ยน IP และเข้า-ออกตลอดเวลา (ตัวอย่าง: BitTorrent, Gnutella)
  3. Hybrid Architecture (ลูกผสม Client-Server + P2P): เช่น Napster ยุคแรก หรือระบบแชต/ค้นหาที่ใช้ เซิร์ฟเวอร์กลางทำหน้าที่เฉพาะการค้นหารายชื่อ (Centralized Directory/Search) แต่เมื่อรู้ว่าไฟล์อยู่ที่ใครแล้ว การโอนย้ายไฟล์จริงจะทำแบบ P2P ระหว่างเครื่องต่อเครื่องโดยตรง

2.1 Domain Name System (DNS)

มนุษย์จดจำชื่อเว็บไซต์ (เช่น www.kmutnb.ac.th) ได้ง่ายกว่าตัวเลข IP แต่เราเตอร์ในชั้น Network Layer รู้จักเฉพาะหมายเลข IP เท่านั้น ระบบ DNS จึงทำหน้าที่เป็น ฐานข้อมูลแบบกระจายตามลำดับชั้น (Distributed Hierarchical Database) เพื่อแปลชื่อโดเมนเป็นหมายเลข IP (ทำงานบน UDP Port 53 เป็นหลัก และใช้ TCP Port 53 เมื่อทำ Zone Transfer หรือข้อมูลตอบกลับใหญ่เกิน 512 bytes):

  • ลำดับการสืบค้น (DNS Resolution Hierarchy): เครื่องเช็คไฟล์ hosts และ Local Cache ➔ ถาม Local DNS Resolver ขององค์กร/ISP ➔ ถ้ายืนยันไม่ได้จะไล่ถามตามลำดับชั้น: 1. Root DNS Server (13 ตระกูลหลักของโลก) ➔ 2. Top-Level Domain (TLD) DNS Server (เช่น .com, .org, .th) ➔ 3. Authoritative DNS Server (เซิร์ฟเวอร์เจ้าของโดเมนจริง เช่น DNS ของ มจพ.)
  • ชนิดของระเบียนข้อมูล (DNS Resource Records):
  • A Record: แปลงชื่อ Hostname เป็นหมายเลข IPv4 (32-bit)
  • AAAA Record: แปลงชื่อ Hostname เป็นหมายเลข IPv6 (128-bit)
  • CNAME Record: ชื่อแฝง (Alias) ชี้ไปยังชื่อจริง (Canonical Name)
  • MX Record: ระบุชื่อเซิร์ฟเวอร์รับส่งอีเมล (Mail Exchanger) ของโดเมนนั้น
  • HTTPS Record: ระเบียนยุคใหม่ที่ใช้เก็บข้อมูล ALPN (HTTP/3) และกุญแจเข้ารหัส ECH (Encrypted Client Hello)

ที่มาที่ไปและเหตุผลเชิงวิศวกรรม (Why It Exists & First Principles)

หากเว็บไซต์วิดีโออย่าง YouTube หรือ Netflix เก็บไฟล์วิดีโอความละเอียดสูง 4K ไว้เป็นไฟล์เดียวขนาดใหญ่ เมื่อผู้ใช้ที่นั่งอยู่ในรถยนต์และสัญญาณมือถือดรอปลงกะทันหัน วิดีโอจะค้างหมุนติ้ว (Buffering) ทันที ในทางกลับกัน หากบีบอัดเป็นความละเอียดต่ำ 360p อย่างเดียว คนที่ใช้เน็ตไฟเบอร์ความเร็วสูงก็จะได้รับภาพที่เบลอไม่คมชัด จึงเกิดเทคโนโลยี DASH (Dynamic Adaptive Streaming over HTTP) ขึ้นมาแก้ปัญหานี้!

Manifest File ของ DASH คืออะไร และมีบทบาทอย่างไร? (คำตอบระดับ Best Answer สำหรับข้อสอบข้อที่ 5)

  1. หลักการของ DASH: บนฝั่งเซิร์ฟเวอร์ วิดีโอ 1 เรื่องจะถูกหั่นออกเป็นชิ้นย่อยๆ ตามเวลา เรียกว่า Chunks / Segments (เช่น ชิ้นละ 2–4 วินาที) และแต่ละชิ้นจะถูกเข้ารหัสบันทึกไว้ หลายระดับความละเอียดและหลายอัตราบิต (Multiple Encoding Rates / Bitrates) เช่น 360p (500 kbps), 720p (2 Mbps), 1080p (5 Mbps), 4K (15 Mbps) เก็บไว้เป็นไฟล์แยกกันบน HTTP Web Server/CDN
  2. Manifest File (.mpd — Media Presentation Description) คืออะไร:
  • คือ "ไฟล์สารบัญหรือแผนผังรายการข้อมูลเมตา (Index / Metadata File)" ที่เซิร์ฟเวอร์ส่งให้เครื่องผู้เล่น (Client) เป็นอันดับแรกสุดก่อนเริ่มเล่นวิดีโอ โดยภายใน Manifest File จะระบุรายการ URL ที่อยู่ของวิดีโอแต่ละก้อน (Chunks) ในทุกระดับความละเอียด/บิตเรต (Encoding Rates) พร้อมข้อมูลเวลาเริ่มต้น-สิ้นสุดและฟอร์แมตของแต่ละก้อน
  1. บทบาทสำคัญของ Manifest File ต่อการทำ Multimedia Streaming:
  • ช่วยให้ ฝั่งผู้รับ (Client) เป็นผู้มีอำนาจตัดสินใจด้วยตนเอง (Client-driven Adaptation): ในขณะเล่นวิดีโอ เครื่อง Client จะวัดความเร็วแบนด์วิดท์ของเครือข่ายและระดับน้ำในบัฟเฟอร์ของตนเองตลอดเวลา แล้วเปิดดู Manifest File เพื่อเลือกส่งคำขอ HTTP GET ไปดึงก้อนวิดีโอชิ้นถัดไปในระดับความละเอียดที่เหมาะสมที่สุด ณ วินาทีนั้น (ถ้าเน็ตแรงก็ดึง URL ของก้อน 4K; ถ้าเน็ตตกก็สลับไปดึง URL ของก้อน 480p ในชิ้นถัดไปได้ทันทีโดยวิดีโอเล่นต่อเนื่องไม่สะดุดค้าง!)

1. รูปแบบสถาปัตยกรรมPublish / Subscribe (ผ่านตัวกลาง Broker): เซ็นเซอร์ทำหน้าที่ Publish ข้อมูลเข้าสู่หัวข้อ (Topic เช่น home/livingroom/temp) ที่ตัว Broker ส่วนมือถือที่กด Subscribe หัวข้อนั้นไว้จะได้รับข้อมูลจาก BrokerRequest / Response (เหมือน HTTP ย่อส่วน): ไคลเอ็นต์ส่งคำขอไปที่เซิร์ฟเวอร์บนเซ็นเซอร์โดยตรง โดยใช้เมธอดเหมือน HTTP ทุกประการ ได้แก่ GET, POST, PUT, DELETE และมีรหัสตอบกลับคล้าย HTTP (เช่น 2.05 Content)

5. กรณีศึกษางานวิจัย: กลไกการทำงานและสถานะปัจจุบันของ Encrypted Client Hello (ECH)

ในชั้นเรียนมีการนำเสนองานวิจัยเรื่อง ECH (Encrypted Client Hello) ซึ่งเข้ามาแก้จุดอ่อนด้านความเป็นส่วนตัวของการเชื่อมต่อ HTTPS (TLS 1.3):

  • ที่มาของปัญหา: แม้เราจะเข้าเว็บไซต์ด้วย HTTPS ที่เข้ารหัสเนื้อหาทั้งหมด แต่ในขั้นตอนแรกสุดของ TLS Handshake เครื่องไคลเอ็นต์จะต้องส่งข้อความ ClientHello ซึ่งระบุชื่อโดเมนเว็บไซต์ปลายทางไว้ในฟิลด์ SNI (Server Name Indication) เป็นข้อความธรรมดาที่ไม่ได้เข้ารหัส (Plaintext) ทำให้ผู้ให้บริการอินเทอร์เน็ต (ISP), ไฟร์วอลล์องค์กร หรือผู้ดักฟังระหว่างทางรู้ได้ทันทีว่าเรากำลังเปิดเข้าเว็บไซต์ชื่ออะไร
  • กลไกของ ECH: ไคลเอ็นต์จะดึงกุญแจสาธารณะของ ECH มาจากระเบียน HTTPS Record ของระบบ DNS แล้วนำมาเข้ารหัสส่วน Inner ClientHello (ที่เก็บชื่อเว็บจริง) จากนั้นห่อใส่ซอง Outer ClientHello ที่โชว์เฉพาะชื่อผู้ให้บริการ CDN กลาง (เช่น cloudflare-ech.com) ทำให้คนภายนอกเห็นแค่ว่าเชื่อมต่อไปยัง Cloudflare แต่ไม่รู้ว่าเข้าเว็บใดข้างใน
  • บทบาทของ GREASE (Generate Random Extension and Sustain Extensibility): คือการที่เว็บเบราว์เซอร์ส่งส่วนขยาย ECH ปลอม (ข้อมูลสุ่ม) ออกไปเป็นประจำแม้เว็บปลายทางจะยังไม่รองรับ ECH จริง เพื่อฝึกและป้องกันไม่ให้อุปกรณ์เครือข่ายตรงกลาง (Middleboxes เช่น Firewall/Proxy รุ่นเก่า) ตกใจและบล็อกแพ็กเก็ตเมื่อมีการเปิดใช้ ECH จริงในอนาคต
  • ผลการวิจัยและผลกระทบ: ปัจจุบันฝั่งเบราว์เซอร์ (Client) มีความพร้อมสูงมาก (พบ ECH extension ใน 59% ของทราฟฟิก QUIC แต่ส่วนใหญ่ยังเป็น GREASE) ขณะที่ฝั่ง Server/DNS ยังรองรับจำกัด (มี Cloudflare เป็นผู้นำหลัก) และความท้าทายสำคัญคือ อุปกรณ์รักษาความปลอดภัย (Firewall/IDS) จะไม่สามารถใช้ SNI ในการกรองเว็บไซต์อันตรายได้เหมือนเดิมอีกต่อไป

ที่มาที่ไปและเหตุผลเชิงวิศวกรรม (Why It Exists & First Principles)

ในเครือข่ายสายแลน (Ethernet) เราใช้โปรโตคอล CSMA/CD (Collision Detection) คือส่งไปฟังไป ถ้าชนกันก็หยุดส่งทันที แต่ในเครือข่ายไร้สาย (IEEE 802.11 Wi-Fi) เราไม่สามารถใช้ Collision Detection (CD) ได้ ด้วยเหตุผลทางฟิสิกส์ 2 ประการ: 1. กำลังส่งของตัวเองกลบสัญญาณอื่นมิด (Self-Signal Overwhelms Incoming Signal): ขณะที่เสาอากาศ Wi-Fi กำลังปล่อยคลื่นส่งออกไปด้วยกำลังสูง มันไม่สามารถรับฟังสัญญาณอ่อนๆ ของคนอื่นที่วิ่งสวนมาชนในเวลาเดียวกันได้เลย 2. ไม่ได้ยินกันทุกโหนด (Hidden Terminal Problem): โหนดสองตัวที่อยู่คนละฝั่งของ Access Point อาจมีสิ่งกีดขวางหรืออยู่ไกลเกินรัศมีของกันและกัน ทำให้ตรวจไม่พบว่ามีการชนกันเกิดขึ้นที่ตัว Access Point ตรงกลาง

ด้วยเหตุนี้ มาตรฐาน 802.11 จึงเปลี่ยนจาก การตรวจจับการชน (CD) มาเป็น CSMA/CA (Carrier Sense Multiple Access with Collision Avoidance — การหลีกเลี่ยงการชนล่วงหน้า) และต้องมีการส่งเฟรม ACK (Link-layer Acknowledgement) ยืนยันกลับทุกครั้งที่รับเฟรมสำเร็จ!

1.1 ปัญหา Hidden Terminal คืออะไร และ 802.11 แก้ไขปัญหานี้อย่างไร? (คำตอบ Best Answer สำหรับข้อสอบข้อที่ 6!)

🏗️ ปัญหาโหนดซ่อนเร้นในเครือข่ายไร้สาย (Hidden Terminal Problem) และการชนกันที่ Access PointArchitecture & Flow Diagram
  1. ปัญหา Hidden Terminal คืออะไร:
  • คือปัญหาที่เกิดขึ้นในเครือข่ายไร้สาย เมื่อมีโหนดผู้ส่ง 2 โหนด (เช่น โหนด A และ โหนด C) ต่างก็อยู่ในรัศมีที่สามารถส่งข้อมูลไปหาโหนดผู้รับตัวเดียวกันตรงกลาง (เช่น Access Point B) ได้ แต่โหนด A และโหนด C อยู่ไกลกันเกินไปหรือมีสิ่งกีดขวางกั้น ทำให้ A และ C ไม่ได้ยินสัญญาณของกันและกัน (ซ่อนตัวจากกัน)
  • ผลที่ตามมาคือ เมื่อโหนด A กำลังส่งข้อมูลให้ B อยู่ โหนด C ซึ่งฟังช่องสัญญาณแล้วไม่พบสัญญาณของ A จึงเข้าใจผิดว่าช่องสัญญาณว่าง (Idle) และตัดสินใจส่งข้อมูลไปหา B พร้อมกันทันที ทำให้เฟรมข้อมูลของ A และ C พุ่งเข้าชนกัน (Collision) ที่ตัวรับ B จนข้อมูลเสียหายทั้งคู่!
  1. มาตรฐาน IEEE 802.11 แก้ไขปัญหานี้อย่างไร (กลไก RTS / CTS Handshake):
  • แก้ไขโดยใช้กลไกการจองช่องสัญญาณล่วงหน้าด้วยเฟรมควบคุมขนาดเล็กที่เรียกว่า RTS (Request to Send) และ CTS (Clear to Send) ร่วมกับตัวตั้งเวลา NAV (Network Allocation Vector):
  1. ก่อนที่ โหนด A จะส่งเฟรมข้อมูลขนาดใหญ่ มันจะส่งเฟรมสั้นๆ ที่ชื่อว่า RTS (Request to Send) ซึ่งระบุระยะเวลาที่จะขอใช้ช่องสัญญาณ ไปให้ Access Point (B) ก่อน
  2. เมื่อ Access Point (B) ได้รับ RTS จะกระจายเฟรมตอบรับ CTS (Clear to Send) ออกไปให้ทุกโหนดในรัศมีของ B ได้ยิน (ซึ่ง ทั้งโหนด A และโหนด C ที่ซ่อนอยู่ จะได้ยินเฟรม CTS จาก B อย่างชัดเจน!)
  3. เมื่อ โหนด C ได้ยินเฟรม CTS จาก B โหนด C จะรู้ทันทีว่ามีคนกำลังใช้ช่องสัญญาณอยู่และจะตั้งเวลาห้ามตัวเองส่งข้อมูล (NAV — Virtual Carrier Sensing) ตลอดช่วงเวลานั้น ส่วน โหนด A เมื่อได้รับ CTS จึงส่งเฟรม DATA จนจบและรับ ACK กลับได้อย่างปลอดภัยไร้การชน!

แนวทางการตอบข้อสอบข้อที่ 7 (2 คะแนน) ให้ได้คะแนนเต็ม:

• ความแตกต่างของระยะเวลา: ในมาตรฐาน 802.11 ระยะเวลา SIFS (Short Interframe Space) มีค่า สั้นกว่า ระยะเวลา DIFS (Distributed Interframe Space) เสมอ ($\text{SIFS} < \text{DIFS}$) โดยโหนดทั่วไปที่ต้องการจะเริ่มต้นแย่งส่งเฟรมข้อมูลใหม่ (DATA) จะต้องฟังให้แน่ใจว่าช่องสัญญาณว่างติดต่อกันเป็นเวลาอย่างน้อยเท่ากับ DIFS เสียก่อนจึงจะมีสิทธิ์ส่งได้

• เหตุผลที่ผู้รับรอเพียง SIFS ก่อนส่ง ACK:

1. เพื่อให้การส่งเฟรม ACK มีลำดับความสำคัญสูงสุด (Highest Priority) เหนือการส่งข้อมูลใหม่ของโหนดอื่น: เนื่องจากหลังจบเฟรม DATA ผู้รับรอเพียงเวลาสั้นๆ เท่ากับ SIFS ก็ส่ง ACK ออกไปทันที ในขณะที่โหนดอื่นๆ ในเครือข่ายยังต้องนั่งรอให้ครบเวลา DIFS (ซึ่งนานกว่า SIFS) 2. ป้องกันไม่ให้โหนดอื่นแทรกกลาง (Prevent Interruption / Collision with ACK): ทำให้โหนดอื่นได้ยินสัญญาณ ACK ก่อนที่เวลา DIFS ของพวกมันจะครบ จึงหยุดรอและไม่ส่งข้อมูลใหม่เข้ามาชนกับเฟรม ACK ช่วยให้ธุรกรรมการรับ-ส่งข้อมูลเดิมจบสมบูรณ์อย่างรวดเร็วและไม่ต้องเสียเวลาส่งเฟรม DATA ก้อนใหญ่ซ้ำใหม่

ข้อที่ 1: การวิเคราะห์ค่า Sampled RTT และการกำหนดค่า RTO [4 คะแนน]

โจทย์: จงพิจารณาค่า Sampled RTT ดังแสดงในภาพ (กราฟแสดงค่า Sampled RTT ที่แกว่งตัวขึ้นลงระหว่าง 1 ms ถึง 7 ms ตามเวลา)

  • 1.1) หากกำหนดให้ค่า RTO เป็นค่าคงที่เท่ากับ 3 ms จะเกิดอะไรขึ้น?
ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: หากกำหนดค่า RTO = 3 ms ซึ่งต่ำกว่าค่า Sampled RTT จริงของเครือข่ายในหลายช่วงเวลา (ที่มีค่าพุ่งขึ้นไปถึง 4–7 ms) จะทำให้ตัวจับเวลาของผู้ส่ง หมดเวลาก่อนที่แพ็กเก็ต ACK จะเดินทางกลับมาถึง (Premature Timeout) ทั้งๆ ที่แพ็กเก็ตไม่ได้สูญหายจริง ส่งผลให้ TCP ทำการ ส่งแพ็กเก็ตซ้ำโดยไม่จำเป็น (Unnecessary / Spurious Retransmissions) ทำให้สิ้นเปลืองแบนด์วิดท์ เพิ่มภาระความแออัด (Congestion) ในเครือข่าย และทำให้ TCP ลดขนาดหน้าต่างการส่งข้อมูลลงโดยไม่จำเป็น

  • 1.2) หากกำหนดให้ RTO มีค่าเท่ากับ 8 ms จะเกิดอะไรขึ้น?
ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: หากกำหนดค่า RTO = 8 ms ซึ่งสูงกว่าค่า Sampled RTT ปกติมากเกินไป เมื่อเกิดเหตุการณ์ แพ็กเก็ตสูญหายจริงในเครือข่าย (Packet Loss) ผู้ส่งจะต้องเสียเวลานั่งรออยู่นานจนครบ 8 ms กว่าจะตรวจพบว่าแพ็กเก็ตหายและเริ่มทำการส่งซ้ำ ส่งผลให้ กระบวนการกู้คืนข้อมูลที่สูญหายล่าช้ามาก (Slow Loss Recovery / Long Timeout Delay) ทำให้ความหน่วงรวมเพิ่มขึ้นและอัตราการส่งข้อมูล (Throughput) ลดลง

  • 1.3) จงอธิบายวิธีการกำหนดค่า RTO ที่ดี:
ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: การกำหนดค่า RTO ที่ดี ต้องไม่ตั้งเป็นค่าคงที่ตายตัว แต่ต้องปรับเปลี่ยนแบบไดนามิกตามสภาพเครือข่ายในแต่ละ Session โดยคำนวณจาก 1) ค่าเฉลี่ยถ่วงน้ำหนักของเวลารอบเดินทาง (EstimatedRTT) ร่วมกับ 2) ค่าความแปรปรวนของ RTT ในเครือข่าย (DevRTT / RTT Variance) ตามสมการ $\text{RTO} = \text{EstimatedRTT} + 4 \times \text{DevRTT}$ เพื่อให้ค่า RTO ปรับตัวครอบคลุมความผันผวนของ RTT ได้อย่างแม่นยำ (ไม่ต่ำเกินไปจนเกิดการส่งซ้ำปลอม และไม่สูงเกินไปจนกู้คืนข้อมูลช้า)

ข้อที่ 2: การวิเคราะห์กราฟ Random Early Detection (RED-1 และ RED-2) [4 คะแนน]

โจทย์: จงพิจารณากราฟที่ใช้ในการทำ Random Early Detection ดังต่อไปนี้ (กราฟ RED-1 มีจุดเริ่มดรอปที่ $\text{AvgLen}=10$, จุดสูงสุดที่ $\text{AvgLen}=15$ มีค่า $P_{\text{drop}}=0.5$; และกราฟ RED-2 มีจุดเริ่มดรอปที่ $\text{AvgLen}=10$, จุดสูงสุดที่ $\text{AvgLen}=15$ มีค่า $P_{\text{drop}}=0.7$ โดยถ้า $\text{AvgLen} > 15$ ค่า $P_{\text{drop}} = 1.0$) ถ้า $P_{\text{Throughput}}$ คือเปอร์เซ็นต์ของจำนวน packet ที่ออกจาก router ต่อจำนวนที่เข้ามาทั้งหมด จงอธิบายว่า $P_{\text{Throughput}}$ ควรจะเป็นกี่เปอร์เซ็นต์ถ้า:

  • 2.1) Average queue length มีค่าเป็น 10 packets และ router ใช้ RED-2: ➔ คำตอบคือ 100%
  • 2.2) Average queue length มีค่าเป็น 18 packets และ router ใช้ RED-1: ➔ คำตอบคือ 0%
  • 2.3) Average queue length มีค่าเป็น 13 packets และ router ใช้ RED-1: ➔ คำตอบคือ 70%
  • 2.4) Average queue length มีค่าเป็น 13 packets และ router ใช้ RED-2: ➔ คำตอบคือ 58%
ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer สำหรับช่อง "อธิบายแนวคิด":

• กราฟของ RED แสดงความน่าจะเป็นในการ ดรอปแพ็กเก็ตทิ้ง ($P_{\text{drop}}$) ดังนั้นสัดส่วนของแพ็กเก็ตที่รอดชีวิตวิ่งออกจากเราเตอร์ได้สำเร็จคือ $P_{\text{Throughput}} = (1 - P_{\text{drop}}) \times 100\%$

• กรณี 2.1 ($\text{AvgLen} = 10$, RED-2): คิวเฉลี่ยยังอยู่ที่ขีดจำกัดเริ่มต้น ($\text{MinThreshold} = 10$) เราเตอร์จึงยังไม่ดรอปแพ็กเก็ตเลย ($P_{\text{drop}} = 0$) ดังนั้นแพ็กเก็ตออกได้ครบ $100\%$

• กรณี 2.2 ($\text{AvgLen} = 18$, RED-1): คิวเฉลี่ยสูงเกินขีดจำกัดสูงสุด ($\text{MaxThreshold} = 15$) เราเตอร์จึงดรอปแพ็กเก็ตที่เข้ามาใหม่ทั้งหมด ($P_{\text{drop}} = 1.0$ หรือ $100\%$) ดังนั้น $P_{\text{Throughput}} = (1 - 1) \times 100\% =$ 0%

• กรณี 2.3 ($\text{AvgLen} = 13$, RED-1): อยู่กึ่งกลางช่วงลาดเอียง $[10, 15]$ ซึ่งใน RED-1 มีความชันถึงค่าสูงสุด $P_{\max} = 0.5$ ที่จุด 15 คำนวณความน่าจะเป็นการดรอปได้เป็น $P_{\text{drop}} = 0.5 \times \frac{13 - 10}{15 - 10} = 0.5 \times \frac{3}{5} = 0.30$ (ดรอปไป $30\%$) ดังนั้นแพ็กเก็ตที่วิ่งออกไปได้คือ $P_{\text{Throughput}} = 100\% - 30\% =$ 70%

• กรณี 2.4 ($\text{AvgLen} = 13$, RED-2): คำนวณด้วยวิธีเดียวกันแต่ใช้ค่า $P_{\max} = 0.7$ ของกราฟ RED-2 จะได้ $P_{\text{drop}} = 0.7 \times \frac{13 - 10}{15 - 10} = 0.7 \times \frac{3}{5} = 0.42$ (ดรอปไป $42\%$) ดังนั้นแพ็กเก็ตที่วิ่งออกไปได้คือ $P_{\text{Throughput}} = 100\% - 42\% =$ 58%

ข้อที่ 3: กลไก Congestion Control และ Flow Control ของ TCP [2 คะแนน]

  • 3.1) Advertised Window คืออะไร?
ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: Advertised Window (rwnd) คือขนาดหน้าต่างรับข้อมูลที่ ฝั่งผู้รับปลายทาง (Destination / Receiver) แจ้งกลับมายังฝั่งผู้ส่ง (ผ่านส่วนหัวของ TCP ACK) เพื่อระบุว่าขณะนั้นบัฟเฟอร์หน่วยความจำของฝั่งผู้รับยังเหลือพื้นที่ว่างรองรับข้อมูลได้อีกเท่าใด มีวัตถุประสงค์เพื่อทำ Flow Control ป้องกันไม่ให้ผู้ส่งส่งข้อมูลเร็วเกินไปจนล้นบัฟเฟอร์ของผู้รับ

  • 3.2) Slow Start ช่วยเพิ่มประสิทธิภาพของการส่งข้อมูลของ TCP อย่างไร?
ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: เมื่อเริ่มเชื่อมต่อ TCP ใหม่ ผู้ส่งยังไม่ทราบขีดความสามารถ (Capacity) ของเครือข่าย กลไก Slow Start จึงเริ่มส่งที่ขนาดหน้าต่างเล็กๆ (cwnd = 1 MSS) แล้ว เพิ่มขนาด cwnd แบบทวีคูณ (Exponential: 1, 2, 4, 8, 16...) ในทุกๆ รอบ RTT ที่ได้รับ ACK การเพิ่มแบบทวีคูณนี้ช่วยให้ TCP สามารถไต่ระดับความเร็วขึ้นไปค้นหาขีดความสามารถสูงสุดที่เครือข่ายรองรับได้ (Available Bandwidth / ssthresh) อย่าง รวดเร็วมาก แทนที่จะเสียเวลาค่อยๆ เพิ่มทีละ 1 แบบเส้นตรงตั้งแต่ต้น จึงใช้ประโยชน์จากแบนด์วิดท์ของเครือข่ายได้อย่างเต็มประสิทธิภาพในเวลาอันสั้น

ข้อที่ 4: คำถามถูกหรือผิดเกี่ยวกับโปรโตคอลชั้น Application Layer [2 คะแนน]

ข้อย่อยข้อความในข้อสอบคำตอบที่ถูกต้องเหตุผลประกอบ (สำหรับทบทวนความเข้าใจ)
4.1MQTT ไม่มีการทำ QoSผิด (X ที่ช่อง ผิด)เพราะ MQTT มีกลไก QoS (Quality of Service) ถึง 3 ระดับ ได้แก่ QoS 0 (At most once), QoS 1 (At least once) และ QoS 2 (Exactly once)
4.2CoAP มีหลักการทำงานคล้าย HTTPถูก (X ที่ช่อง ถูก)เพราะ CoAP ใช้สถาปัตยกรรมแบบ Request/Response และใช้คำสั่ง GET, POST, PUT, DELETE พร้อมรหัสสถานะคล้ายกับ HTTP ทุกประการ (แต่ออกแบบให้มีขนาดเล็กและรันบน UDP)
4.3POP3 เป็นโปรโตคอลสำหรับใช้ส่งข้อมูลระหว่าง mail serverผิด (X ที่ช่อง ผิด)เพราะโปรโตคอลที่ใช้ส่งข้อมูลระหว่าง Mail Server คือ SMTP ส่วน POP3 ใช้สำหรับให้เครื่องผู้ใช้ดึงเมลจาก Mail Server มาอ่านเท่านั้น
4.4EMAIL เป็นแอปพลิเคชันที่รันอยู่บน TCPถูก (X ที่ช่อง ถูก)เพราะโปรโตคอลอีเมลทั้งหมด (SMTP, POP3, IMAP) ต้องการความน่าเชื่อถือสูง ห้ามข้อมูลสูญหาย จึงรันอยู่บน TCP ทั้งหมด

ข้อที่ 5: บทบาทของ Manifest File ในการทำสตรีมมิ่งด้วย DASH [3 คะแนน]

โจทย์: DASH หรือ Dynamic Adaptive Streaming over HTTP เป็นแอปพลิเคชันที่ถูกออกแบบมาเพื่อทำ Multimedia Streaming จงอธิบายว่า Manifest File ของ DASH คืออะไร และมีบทบาทต่อการทำ multimedia streaming อย่างไร

ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: 1. Manifest File คืออะไร: ในระบบ DASH ไฟล์วิดีโอบนเซิร์ฟเวอร์จะถูกแบ่งออกเป็นชิ้นย่อยๆ ตามเวลา (Chunks / Segments) และแต่ละชิ้นจะถูกเข้ารหัสไว้หลายระดับคุณภาพ/อัตราบิต (Multiple Encoding Rates / Bitrates) โดย Manifest File (.mpd) คือ ไฟล์รายการสารบัญที่เก็บที่อยู่ URL และข้อมูลความละเอียด/อัตราบิตของวิดีโอแต่ละก้อนทั้งหมด 2. บทบาทต่อการทำ Multimedia Streaming: Manifest File ช่วยให้เครื่องผู้รับ (Client) ทราบว่าวิดีโอแต่ละก้อนในแต่ละระดับความคมชัดเก็บอยู่ที่ URL ใดบ้าง ทำให้ในระหว่างที่เล่นวิดีโอ Client สามารถวัดความเร็วแบนด์วิดท์ของเครือข่ายตนเองแบบเรียลไทม์ แล้วใช้ข้อมูลจาก Manifest File เลือกร้องขอ (HTTP GET) ก้อนวิดีโอชิ้นถัดไปในระดับคุณภาพ (Encoding Rate) ที่เหมาะสมกับสภาพอินเทอร์เน็ตในขณะนั้นได้เองโดยอัตโนมัติ ช่วยให้เล่นวิดีโอได้อย่างลื่นไหลต่อเนื่องโดยไม่เกิดอาการค้าง (Stalling/Buffering) แม้ความเร็วอินเทอร์เน็ตจะแกว่งตัว

ข้อที่ 6: ปัญหา Hidden Terminal และวิธีแก้ไขของมาตรฐาน IEEE 802.11 [3 คะแนน]

โจทย์: ปัญหา Hidden Terminal คืออะไร และ 802.11 แก้ไขปัญหานี้อย่างไร

ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: 1. ปัญหา Hidden Terminal คือ: สถานการณ์ในเครือข่ายไร้สายที่โหนดผู้ส่ง 2 โหนด (เช่น โหนด A และ โหนด C) อยู่ห่างกันหรือมีสิ่งกีดขวางจน มองไม่เห็นและไม่ได้ยินสัญญาณของกันและกัน แต่ทั้งสองโหนดต้องการส่งข้อมูลไปหาผู้รับตัวเดียวกันตรงกลาง (เช่น Access Point B) เนื่องจาก A และ C ไม่ได้ยินกันจึงเข้าใจว่าช่องสัญญาณว่างและส่งข้อมูลออกมาพร้อมกัน ทำให้เกิด การชนกันของข้อมูล (Collision) ที่ตัวผู้รับ B 2. วิธีแก้ไขของ 802.11: ใช้กลไก CSMA/CA ร่วมกับการแลกเปลี่ยนเฟรมควบคุม RTS (Request to Send) และ CTS (Clear to Send) โดยก่อนที่โหนดผู้ส่ง (A) จะส่งข้อมูลจริง จะส่งเฟรมสั้นๆ RTS ไปขออนุญาตที่ Access Point (B) ก่อน เมื่อ B ได้รับจะส่งเฟรม CTS กระจายออกไปให้ทุกโหนดในรัศมีได้ยิน เมื่อโหนด C ที่ซ่อนอยู่ได้ยินเฟรม CTS จาก B โหนด C จะทราบว่าช่องสัญญาณถูกจองแล้วจึงระงับการส่งข้อมูลของตนเอง (ตั้งค่า NAV) จนกว่าโหนด A จะส่งข้อมูลเสร็จและได้รับ ACK เรียบร้อย

ข้อที่ 7: เหตุผลที่ 802.11 ใช้ระยะเวลารอ SIFS สำหรับ ACK แทนที่จะใช้ DIFS [2 คะแนน]

โจทย์: เหตุใด 802.11 จึงใช้วิธี delay การส่ง ACK packet เป็นระยะเวลาเท่ากับ SIFS (Short Interframe Space) แทนที่จะรอเท่ากับ DIFS (Distributed Interframe Space)

ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: เนื่องจากระยะเวลา SIFS มีค่าสั้นกว่า DIFS เสมอ ($\text{SIFS} < \text{DIFS}$) ในขณะที่โหนดอื่นๆ ที่ต้องการจะเริ่มต้นส่งเฟรมข้อมูลใหม่จะต้องรอให้ช่องสัญญาณว่างครบระยะเวลา DIFS เสียก่อน การให้ผู้รับถ่วงเวลารอเพียงแค่ SIFS แล้วส่งเฟรม ACK ออกไปทันที จะช่วยให้ เฟรม ACK มีลำดับความสำคัญสูงสุด (Highest Priority) เหนือการส่งข้อมูลใหม่ของทุกโหนด ป้องกันไม่ให้โหนดอื่นแทรกส่งข้อมูลเข้ามาชนกับเฟรม ACK ก่อนที่กระบวนการรับ-ส่งเฟรมปัจจุบันจะเสร็จสมบูรณ์

ข้อที่ 8: ความแตกต่างระหว่างเครือข่าย 3G และ 4G [2 คะแนน]

โจทย์: อธิบายความแตกต่างระหว่าง 3G และ 4G Network

ข้อสังเกตและแนวคิดสำคัญ (Key Concept)

Best Answer: ความแตกต่างทางสถาปัตยกรรมที่สำคัญที่สุดคือ:

• เครือข่าย 3G: มีโครงสร้างเครือข่ายหลักแบบผสม (Hybrid Core) ที่ยังแยกเส้นทางการทำงานออกเป็น 2 ส่วน คือ ทราฟฟิกเสียง (Voice) วิ่งผ่านเครือข่ายโทรศัพท์พื้นฐานแบบสลับวงจรเดิม (Circuit-Switched Network ผ่าน MSC) ส่วน ทราฟฟิกข้อมูลอินเทอร์เน็ต (Data) วิ่งผ่านเครือข่ายแพ็กเก็ต (Packet-Switched Network ผ่าน SGSN/GGSN)

• เครือข่าย 4G (LTE): เปลี่ยนโครงสร้างเป็นเครือข่าย All-IP (Packet-Based Network) ทั้งหมด 100% โดยยกเลิกระบบสลับวงจรแบบเดิมออกไปทั้งหมด ทำให้ทั้งข้อมูลอินเทอร์เน็ตและเสียงสนทนา (VoLTE) ถูกรวมให้วิ่งอยู่ในรูปแบบของ IP Packets บนโครงข่ายหลักชุดเดียวกัน ส่งผลให้มีความเร็วสูงขึ้นและมีความหน่วงต่ำลง
